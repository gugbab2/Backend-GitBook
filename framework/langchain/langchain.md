# LangChain 실무 지식

> 부모 문서가 “왜 나왔고 언제 쓰나”라면, 이 페이지는 “어떻게 동작하나”다. LangChain 으로 LLM 을 호출하는 코드를 읽거나 직접 쓸 때 필요한 지식을 모았다.

## 1. 메시지 모델 — 대화는 메시지 리스트다

LLM 호출의 입력은 문자열 하나가 아니라 **역할이 붙은 메시지 리스트**다:

| 타입              | 역할                              |
| --------------- | ------------------------------- |
| `SystemMessage` | 모델에게 주는 지시·역할 설정                |
| `HumanMessage`  | 사용자 발화                          |
| `AIMessage`     | 모델 응답. 이전 턴의 응답도 이 타입으로 이력에 넣는다 |
| `ToolMessage`   | 도구 실행 결과를 모델에게 돌려줄 때            |

LLM 은 지난 대화를 기억하지 않으므로(stateless), “이어지는 대화”를 만들려면 **매 호출마다 이력 전체 리스트를 다시 보낸다.** 이력을 어디에 저장하고 어떻게 재구성할지는 전적으로 앱의 책임이다.

## 2. 모델 호출 3형태

모든 chat model(`BaseChatModel` 구현체)은 같은 메서드를 갖는다:

* `invoke(messages)` — 완성된 `AIMessage` 하나를 반환. 내부적으로는 조각을 받아 합치고 있다
* `stream(messages)` — `AIMessageChunk`(응답 조각)를 하나씩 내버림. 사용자에게 실시간 표시 가능
* `batch([messages, ...])` — 여러 건을 한꺼번에 (예: 대량 분류 작업)

각각 `ainvoke`/`astream`/`abatch` 라는 비동기(async) 버전도 있다.

## 3. 스트리밍 다루기 — 실수가 가장 잦은 영역

**조각(`AIMessageChunk`)에 대해 알아야 할 사실:**

1. **빈 content 조각이 앞서서 올 수 있다.** 첫 조각은 역할 정보만 실리고 텍스트가 비어 있기도 하다. “사용자에게 보인 첫 텍스트”를 기준으로 삼으려면 `chunk.content != ""` 로 판정한다.
2. **조각은 `+` 로 합친다.** 다 모은 뒤 `message_chunk_to_message()` 를 거치면 완성 `AIMessage` 가 된다. 단 `+` 는 매번 누적 내용을 복사한 새 객체를 만든다 — 조각마다 `combined += chunk` 하면 조각 수의 제곱으로 비싸진다. 리스트에 모았다가 마지막에 한 번에 합친다.
3. **`stream()` 의 실체는 파이썬 제너레이터다.** 선언 타입은 `Iterator` 지만 실제 구현이 제너레이터라 `.close()` 를 부를 수 있고, 그러면 진행 중이던 HTTP 응답 연결이 끊겨 **프로바이더 쪽 토큰 생성이 중단**된다. 사용자가 떠난 응답을 끝까지 생성하며 과금되는 걸 막는 유일한 수단이므로, 스트리밍 코드는 모든 종료 경로에서 close 가 보장되게 짜야 한다.

**스트리밍과 재시도의 긴장 관계:**

`invoke()` 는 실패 시 통째로 재시도하면 그만이다 — 사용자는 아직 아무것도 못 봤다. 스트리밍은 이미 화면에 글자가 나간 뒤 재시도하면 **같은 내용이 두 번 출력**된다. 그래서 재시도 허용 구간을 “첫 가시 텍스트가 나오기 전”까지로 좁히고, 그 구간만 별도 함수로 떼어 재시도 로직을 그쪽에만 붙이는 패턴이 쓰인다. 그 이후 오류는 재시도 없이 그대로 올린다.

## 4. 토큰과 사용량

* **사용량(`usage_metadata`)은 완성 응답, 즉 마지막 조각에만 실려 온다.** 스트림이 중간에 끊기면 이번 호출의 정확한 토큰 소모량을 알 수 없다. 과금 집계가 중요한 서비스라면 “단절 시 기록 포기 vs 추정치 기록”을 설계 단계에서 정해야 한다.
* `get_num_tokens_from_messages(messages)` 로 호출 전에 입력 토큰을 재서, 모델의 컨텍스트 한도(한 번에 받을 수 있는 최대 토큰 수)를 넘기 전에 차단할 수 있다.

## 5. 구조화 출력

`llm.with_structured_output(MyPydanticModel)` — 응답을 자유 문장이 아니라 내가 정의한 Pydantic 객체로 받는다. “JSON 으로 답해” 프롬프트 + 파싱 + 실패 재요청을 직접 짜는 대신, 프로바이더의 전용 기능(function calling/JSON mode)을 알아서 골라 쓴다. 분류·추출·판단 같은 “기계가 읽을 응답”에는 이게 기본이고, 사람이 읽을 자연어 응답에는 일반 호출을 쓴다.

## 6. RunnableConfig — 실행별 맥락 전달

`config["configurable"]` 라는 dict 에 실행별 맥락(사용자 ID, 테넌트 스키마 등)을 담아 호출 체인을 따라 내려보내는 LangChain 관례다. 전역 변수나 스레드-로컬 없이 맥락을 전달하는 용도이며, LangGraph 없이도 독립적으로 쓰인다.

## 7. 부록 — 스트리밍 코드를 위한 파이썬 제너레이터 계약 4가지

스트리밍 파이프라인을 직접 짜면 결국 제너레이터 체인이 된다. 이 네 가지를 모르면 막힌다:

1. 제너레이터는 `return 값`을 가질 수 있고, `result = yield from gen` 은 그 반환값을 받는다. (조각을 전부 흘린 뒤 집계 결과를 호출자에게 돌려주는 계약을 만들 수 있다)
2. `for` 루프는 그 반환값을 버린다. 받으려면 수동 `next()` 루프에서 `except StopIteration as stop: stop.value` 로 꺼낸다.
3. 소비자가 제너레이터를 `close()` 하면 멈춰 있던 `yield` 지점에 `GeneratorExit` 예외가 던져진다 → `except GeneratorExit`/`finally` 로 정리(로그, 상류 스트림 close)할 기회를 얻는다.
4. `yield from` 은 close/예외를 아래 제너레이터까지 자동 전파하지만, 수동 `next()` 루프는 전파하지 않는다 → 수동 루프를 쓴 쪽이 아래 제너레이터의 close 를 직접 책임져야 한다.

“응답 조각을 중계하면서, 완주 시 집계 결과를 넘기고, 단절 시 상류 요청까지 끊는” 종류의 코드는 전부 이 네 가지의 조합으로 읽혀진다.
