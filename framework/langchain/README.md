# LangChain

> 이 문서는 [LangGraph](../langgraph/) 문서와 짝으로 읽는다. 두 프레임워크는 경쟁 관계가 아니라 **역할이 다른 계층 관계**다.
>
> * **LangChain = 부품**: LLM 을 호출하는 데 필요한 도구들 (모델 호출 클라이언트, 메시지 타입 등)
> * **LangGraph = 배선**: 그 부품들을 어떤 순서와 조건으로 실행할지 지휘하는 틀
>
> 따라서 “둘 중 무엇을 쓰나”가 아니라 “각 계층을 직접 짜야 하나, 프레임워크에 맡겨도 되나”가 올바른 질문이다.

## 1. 한 줄 정의

LLM 을 호출할 때마다 반복되는 공통 작업을 대신해 주는 도구 모음이다.

* 여러 LLM 서비스 벤터 API 차이 흡수,&#x20;
* 대화 메시지 관리,&#x20;
* 스트리밍(응답을 토막토막 받기),
* 응답을 정해진 형식(JSON)으로 받기
* 등등 ..&#x20;

중요한 특징: LangChain 은 **라이브러리로도, 프레임워크로도 쓸 수 있다.** 이 둘의 차이부터 풀면:

* **라이브러리**: 내 코드가 주인이고, 필요할 때 도구를 꺼내 쓴다. (예: Python 의 `requests`)
* **프레임워크**: 틀이 주인이고, 내 코드를 틀의 정해진 자리에 끼워 넣는다. 실행 순서를 틀이 정한다. (예: Django)

LangChain 을 둘러싼 논쟁은 대부분 이 이중성에서 나온다. “라이브러리로 쓰는 LangChain”과 “프레임워크로 쓰는 LangChain”은 평가가 완전히 다르다 (§6).

## 2. 왜 나왔나 — 2022년, LLM API 를 날것으로 쓰던 시대의 문제

LangChain 은 2022년 10월 공개됐다(ChatGPT 공개 한 달 전). 당시 LLM 앱을 만들려면 아래 문제들을 전부 개발자가 직접 해결해야 했다:

| 문제             | 풀어서 설명하면                                                                                                                                                 |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 회사마다 다른 API    | LLM 을 API 로 파는 회사(OpenAI, Anthropic, Google … 이런 회사를 **프로바이더**라 부른다)마다 요청/응답 형식이 제각각이다. 한 회사 기준으로 코드를 짜면 다른 회사로 갈아타기 어려워진다 (이 상태를 **종속, lock-in** 이라 한다) |
| 대화 기억이 없음      | LLM 은 HTTP 처럼 **stateless** — 지난 대화를 전혀 기억하지 않는다. “이어서 대화하는 것처럼” 보이려면 매 호출마다 지금까지의 대화 전체를 다시 보내야 하고, 그 목록 관리는 개발자 몫이다                                    |
| 출력이 자유 문장      | “JSON 으로 답해” 해도 설명 문장이 섞여 온다. 파싱 실패 → 재요청 코드를 매번 반복해 짜게 된다                                                                                               |
| 문서 기반 답변 부품 없음 | “내 문서를 근거로 답하게 하기”(**RAG** 라 부르는 기법: 질문과 관련된 문서를 먼저 찾아와서 그걸 함께 보여주고 답하게 함)에 필요한 문서 읽기·쪼개기·검색을 전부 직접 만들어야 했다                                              |
| 반복되는 밑작업 코드    | 실패 시 재시도, 장애 시 예비 수단으로 교체(**폴백**), 토큰 수 세기 같은 — 핵심 로직은 아니지만 매번 또 써야 하는 코드(**보일러플레이트**라 부른다)                                                              |

LangChain 의 답: **공통 사용법 하나로 통일하고(추상화), 외부 도구 연결은 미리 만들어 놓자(통합 생태계).** `BaseChatModel` 이라는 공통 인터페이스 하나만 알면 어떤 프로바이더든 같은 방식으로 부를 수 있다.

> 여기서 **추상화**란: 세부 구현의 차이를 감추고 공통 사용법만 남기는 것. Django 의 ORM 이 PostgreSQL/MySQL 차이를 감추고 같은 쿼리 문법을 주는 것과 같은 원리다.

## 3. 지금의 LangChain — 패키지 계층

현재(1.x)는 여러 패키지로 계층이 나뉘어 있고, **어느 계층까지 갖다 쓰느냐가 나중의 수정 비용을 결정한다.**

```
langchain-core        ← 공통 인터페이스·메시지 타입. 가장 안정적 (바뀌는 일이 거의 없음)
langchain-openai 등   ← 프로바이더별 구현체 (AzureChatOpenAI, ChatAnthropic …)
langchain-community   ← 서드파티 도구 연결 모음
langchain             ← 고수준 진입점. 1.0 부터 create_agent 중심 (내부는 LangGraph)
langchain-classic     ← 1.0 에서 밀려난 예전 방식 코드들 (구 Chain 류)
```

실무에서 가치가 검증된 핵심 부품 세 가지 (이것만 쓰는 게 “라이브러리 모드”다):

* **모델 클라이언트**: 어떤 프로바이더든 `.invoke()`(한 번에 받기) / `.stream()`(토막토막 받기) 같은 동일한 메서드로 호출
* **메시지 타입**: 사용자 발화는 `HumanMessage`, 모델 응답은 `AIMessage`, 스트리밍 조각은 `AIMessageChunk` — 조각들은 `+` 연산 하나로 완성 응답으로 합쳐진다. 토큰 사용량도 `usage_metadata` 라는 표준 자리에 실려 온다
* **구조화 출력**: `with_structured_output(내모델)` — 응답을 자유 문장이 아니라 내가 정의한 형식(Pydantic 객체)으로 받는다. 형식 지정 방법이 프로바이더마다 다른 걸 대신 흡수해 준다

## 4. 역사 — 고수준 추상은 3번 갈아엎어졌다

| 시기      | 사건                                                                              | 지금 상태                                |
| ------- | ------------------------------------------------------------------------------- | ------------------------------------ |
| 2022-10 | 공개. `LLMChain` 등 **Chain**(호출을 순서대로 이어 붙이는 틀) 중심                                | 폐기                                   |
| 2023    | **AgentExecutor**(LLM 이 도구를 고르며 알아서 도는 자동 루프) 전성기                               | 폐기 — 내부를 손볼 수 없다는 비판, LangGraph 로 대체 |
| 2023-08 | **LCEL** (호출들을 파이프라인처럼 연결하는 전용 문법)                                              | 단순 연결엔 유효, 복잡한 흐름엔 비권장               |
| 2024-01 | 0.1 — 안정화 선언, `langchain-core` 분리                                               |                                      |
| 2024\~  | 0.2 / 0.3 (패키지 추가 분리)                                                           |                                      |
| 2025-10 | **1.0** — `create_agent` 중심 재편(내부는 LangGraph), 예전 방식은 `langchain-classic` 으로 분리 | 현행                                   |

> **이 표 자체가 가장 중요한 교훈이다.** 3년 동안 _실행 흐름을 대신 정해 주는 고수준 틀_ (Chain → AgentExecutor → LCEL → create\_agent) 은 세 번 갈아엎어졌지만, _부품 계층_ (메시지 타입·모델 클라이언트·구조화 출력) 은 거의 그대로 살아남았다. 무엇에 의존하면 안전하고 무엇이 유행인지를, 프레임워크 자신의 역사가 보여준 셀이다.

## 5. 강점과 비판

**강점**

* 프로바이더 교체가 쉬워진다 — 특정 회사에 묶이지 않음
* 스트리밍·토큰 사용량·구조화 출력을 표준 방식 하나로 — 직접 만들면 프로바이더마다 다시 만들어야 함
* 외부 도구 연결이 미리 만들어져 있음 — RAG 부품 조립이 빠름

**비판** — “Why we no longer use LangChain”(우리는 이제 LangChain 을 안 쓴다) 류의 이탈 글이 한 시기 유행했을 만큼 유명하다

* **과추상화**: 감추지 않아도 될 것까지 감췄다. 단순 API 호출 하나에 포장이 여러 겹이어서, 정작 모델에게 무슨 프롬프트가 실제로 나가는지 보기 어렵다
* **디버깅 난이도**: 오류가 나면 스택트레이스가 내 코드가 아니라 프레임워크 내부를 지나간다
* **잦은 변경**: 버전이 오를 때마다 임포트 경로와 권장 사용법이 바뀌던 시기가 길었다 (1.0 에서 안정화 선언)
* **타입이 느슨함**: 범용성을 위해 반환 타입을 넓게 잡아서, 받는 쪽 코드의 타입 검사 효용이 떨어진다

핵심은 이 비판 대부분이 **고수준(프레임워크 모드) 계층을 향한 것**이라는 점이다. 부품 계층에 대한 평가는 업계에서도 대체로 긍정적이다.

## 6. 언제 쓰고 언제 안 쓰나

**라이브러리 모드로 쓰기 좋은 경우** (실행 흐름은 내 코드가 갖고, LangChain 은 부품만)

* 프로바이더를 갈아탈 가능성이 있거나, 그 선택지를 열어두고 싶을 때
* 메시지 타입·스트리밍 조각 병합·토큰 집계·구조화 출력을 직접 만들고 싶지 않을 때
* RAG 부품을 조립할 때

**안 쓰는 게 나은 경우**

* 프로바이더 하나로 확정했고, 요청/응답을 세밀하게 제어해야 할 때 → 그 회사의 공식 SDK 가 더 단순하고 투명하다
* 프레임워크 모드(`create_agent` 등에 실행 흐름을 맡기는 것)가 부담이면 그 계층만 안 쓰면 된다 — 전부 쓰거나 전부 버리거나의 양자택이 아니다

> **실무 지침: “프레임워크가 아니라 라이브러리로 쓴다.”** 무엇을 언제 호출하고 어떻게 분기할지는 내 코드가 갖고, LangChain 에는 프로바이더 차이 흡수· 메시지 타입·구조화 출력만 맡긴다. 이렇게 쓰면 §4 의 역사에서 안정적으로 살아남은 계층에만 의존하게 된다.

## 용어 정리

| 용어           | 뜻                                                         |
| ------------ | --------------------------------------------------------- |
| 프로바이더        | LLM 을 API 로 서비스하는 회사 (OpenAI, Anthropic, Google 등)        |
| 종속 (lock-in) | 특정 회사/도구에 맞춰 코드를 짜서 다른 곳으로 갈아타기 어려워진 상태                   |
| stateless    | 지난 요청/대화를 기억하지 않음. 매번 필요한 맥락을 전부 다시 보내야 함                 |
| 보일러플레이트      | 핵심 로직은 아니지만 매번 반복해서 써야 하는 밑작업 코드                          |
| 추상화          | 세부 구현 차이를 감추고 공통 사용법만 남기는 것 (예: ORM)                      |
| 폴백           | 주 수단이 실패했을 때 자동으로 대신 쓰는 예비 수단                             |
| 구조화 출력       | 응답을 자유 문장이 아니라 JSON 같은 정해진 형식으로 받는 것                      |
| RAG          | 질문과 관련된 문서를 먼저 검색해서, 그 문서를 근거로 LLM 이 답하게 하는 기법            |
| 임베딩 / 벡터스토어  | 텍스트를 의미가 비슷하면 가까워지는 숫자 배열로 바꾸는 것 / 그걸 저장하고 유사한 것을 찾아주는 DB |
| 스트리밍         | 응답을 다 만들어질 때까지 기다리지 않고, 생성되는 족족 토막토막 받아 보여주는 방식           |
