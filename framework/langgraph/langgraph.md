# LangGraph 실무 지식

> 부모 문서가 “왜 나왔고 언제 쓰나”라면, 이 페이지는 “어떻게 동작하나”다. LangGraph 로 짜인 코드를 읽거나, 쓰거나, 순수 파이썬으로 번역할 때 필요한 지식을 모았다.

## 1. 그래프 조립 4단계

```python
# ① 상태 정의 — 모든 단계가 공유하는 데이터 구조
class State(TypedDict):
    messages: Annotated[list, add_messages]   # reducer 부착: 덮어쓰지 않고 몹에 추가
    metadata: dict                            # reducer 없음: 반환하면 통째로 교체

# ② 노드 — 상태를 받아 변경분(dict)을 반환하는 보통의 함수
def extract(state: State, config) -> dict: ...

# ③ 엣지 — 순서와 분기 선언
graph = StateGraph(State)
graph.add_node("extract", extract)
graph.add_edge(START, "extract")
graph.add_conditional_edges("extract", route, ["recommend", "reply"])

# ④ 컴파일 — 선언을 실행 가능한 앱으로
app = graph.compile()          # 영속이 필요하면 compile(checkpointer=...)
```

알아둘 세부 사항:

* **reducer**: 노드 반환값을 기존 상태에 어떻게 합칠지 정하는 병합 규칙 함수. `Annotated[list, add_messages]` 처럼 키에 붙인다. reducer 없는 키는 단순 교체된다.
* **`MessagesState`**: `messages` 키 + `add_messages` reducer 가 미리 세팅된 기성 상태 클래스. 이걸 상속해서 필드를 추가하는 코드가 많다.
* **조건 분기 라우터의 계약**: `route` 함수는 상태를 보고 **다음 노드의 이름 문자열**을 반환한다. 분기 로직이 프레임워크 구문(문자열 매칭)에 묶이는 지점이다 — 순수 파이썬으로 번역하면 그냥 `if 조건:` + bool 함수가 된다.

## 2. 실행과 스트리밍 — stream\_mode 별 출력 형식

`app.invoke(입력)` 은 최종 상태만 반환하고, `app.stream(입력, stream_mode=...)` 은 진행 과정을 실시간으로 내보낸다. **모드마다 내보내는 값의 형태가 다르다** — 소비 코드를 읽는 열쇠다:

| 모드         | 언제 방출되나              | 무엇이 오나                                                          |
| ---------- | -------------------- | --------------------------------------------------------------- |
| `values`   | 매 단계 후               | 그 시점의 상태 전체                                                     |
| `updates`  | 노드 하나가 끝날 때마다        | `{노드이름: 반환값}` dict                                              |
| `messages` | 노드 안 LLM 이 토큰을 낼 때마다 | `(chunk, metadata)` 튜플. `metadata["langgraph_node"]` 로 발생 노드 구분 |
| `custom`   | 노드가 직접 방출할 때         | 노드가 넘긴 임의 값                                                     |

여러 모드를 리스트로 주면 `(모드이름, payload)` 튜플로 섮여 온다.

특히 `messages` 모드는 이해가 중요하다: 이건 **프레임워크가 노드 내부의 LLM 호출을 가로채서 밖으로 흘려주는 채널**이다. 노드 코드는 `invoke()` 로 짜도, 소비자는 토큰을 실시간으로 받는다. 따라서 LangGraph 를 걸어내면 이 채널도 같이 사라지므로, 응답 단계를 LLM 클라이언트 직접 스트리밍(`stream()`)으로 바꿔야 한다 — 제거와 스트리밍 전환이 항상 한 묶음으로 다니는 이유다.

## 3. 실행 모델 주의점 — 내 코드가 도는 스레드

compile 된 그래프는 라운드(super-step) 단위로 돈다: “지금 실행 가능한 노드 수집 → (병렬) 실행 → 결과를 상태에 반영”. 병렬 실행을 위해 **자체 스레드 풀**을 쓰기 때문에, 분기 없는 순차 그래프조차 설정 조합(예: `messages` 스트리밍 모드)에 따라 노드가 요청 스레드가 아닌 별도 스레드에서 실행될 수 있다.

왜 중요한가: **스레드마다 따로 보관되는 자원**과 충돌한다. 대표 예가 Django 의 DB 커넥션이다 — 스레드별로 관리되고(스레드-로컬), Django 의 기본 정리 로직은 요청 스레드 커넥션만 닫는다. 프레임워크 스레드에서 열린 커넥션은 이 정리의 눈에 안 띄어 반납되지 않고 쌓일 수 있고, 커넥션 풀 고갈로 이어질 수 있다. LangGraph 위에서 웹 프레임워크를 쓸 때는 노드 경계에서 자원 정리를 직접 챙겨야 한다.

## 4. 상태 영속 — checkpointer

`compile(checkpointer=PostgresSaver(...))` 처럼 저장소를 붙이고, 실행할 때 `config={"configurable": {"thread_id": "대화ID"}}` 를 넘기면:

* 매 단계마다 상태 스냅샷이 저장된다 (게임 세이브 포인트)
* 같은 `thread_id` 로 다시 실행하면 이전 상태에서 이어진다 (서버 재시작 무관)
* 과거 스냅샷으로 되돌아가 그 지점부터 다시 실행할 수 있다 (time-travel 디버깅)

**checkpointer 를 안 붙이면 상태는 한 번의 실행 안에서만 산다.** 코드를 읽을 때 “이 상태는 어디까지 살아있나”를 판단하는 기준이 된다 — checkpointer 없는 그래프의 상태 키들은 전부 “이번 실행 한정” 임시 값이다.

## 5. 사람 개입과 병렬 — interrupt / Send

* **interrupt**: 노드 안에서 `interrupt("승인해 주세요")` 를 부르면 실행이 멈추고 상태가 저장된다. 나중에 사람 입력을 `Command(resume=값)` 으로 넣어 멈춘 지점부터 재개한다. checkpointer 가 전제다 (멈춤 = 상태 저장).
* **Send**: 라우터가 `Send("노드이름", 개별입력)` 목록을 반환하면 같은 노드가 입력별로 N개 복제돼 병렬 실행되고(fan-out), 결과는 reducer 가 한 상태로 모은다.

둘 다 “쓰고 있느냐 아니냐”가 중요하다: 이 기능들이 LangGraph 가 직접 구현하기 어려운 가치를 제공하는 부분이고, 하나도 안 쓰고 있다면 그 그래프는 순수 파이썬으로 대체 가능하다 (부모 문서 §5·§6 참조).

## 6. 프레임워크 없이 하면? — 개념 대응표

이 표가 있으면 LangGraph 코드를 순수 파이썬으로, 또는 그 반대로 번역할 수 있다:

| LangGraph 개념                    | 순수 파이썬 대응                           |
| ------------------------------- | ----------------------------------- |
| `add_node` + `add_edge` 순차 연결   | 함수를 순서대로 호출                         |
| 조건 분기 라우터 (노드 이름 반환)            | `if 조건:` + bool 함수                  |
| `updates` 모드 소비 (노드명 디스패치)      | 방금 부른 함수의 반환값을 바로 사용                |
| `messages` 모드 (LLM 토큰 가로채기)     | LLM 클라이언트를 직접 `stream()` 하는 제너레이터   |
| 상태 dict + reducer               | 함수 간에 dict 를 직접 update              |
| checkpointer / interrupt / Send | 대응물 없음 — 이게 필요해지는 순간이 프레임워크 도입 시점이다 |

마지막 줄이 양방향 판단 기준이다: 위 세 기능이 필요 없는 그래프는 순수 파이썬 쪽이 단순하고(스택 투명·타입 정확·스레드 걱정 없음), 필요한 순간 직접 구현은 사실상 프레임워크 재발명이 된다.
