# LangGraph

> 짝 문서: [LangChain](../langchain/). LangChain = 부품, LangGraph = 배선. 이 문서 후반(§6)에 **도입·제거 판단 기준**이 있다.

## 1. 한 줄 정의

LLM 작업 흐름을 **상태(state) + 단계(node) + 연결선(edge)의 그래프**로 그려서 선언하면, 그 그래프를 프레임워크가 대신 실행해 주는 **오케스트레이션 프레임워크**다.

> **오케스트레이션**이란: 여러 작업을 어떤 순서로, 어떤 조건에서, 무엇을 병렬로 실행할지 지휘하는 일. 지휘자(orchestrator)가 오케스트라를 이끕듯, 이 역할을 코드 대신 프레임워크가 맡는다.

핵심 단어는 “대신 실행”이다. LangGraph 도입은 그래프 문법을 배우는 일이 아니라, **내 코드가 언제 어느 스레드에서 어떻게 실행될지를 프레임워크에 넘기는 결정**이다 (§4). Celery 에 태스크를 넘기면 언제 어느 워커가 실행할지 Celery 가 정하는 것과 같은 종류의 위임이다.

## 2. 왜 나왔나 — 2024년, “에이전트 루프”의 문제

먼저 용어 하나: **에이전트**란 LLM 이 스스로 판단해서 도구(검색, 계산기, DB 조회 등)를 골라 쓰고, 그 결과를 보고 다음 행동을 다시 정하는 방식의 프로그램을 말한다.

LangChain 의 기존 도구로는 이걸 제대로 만들 수 없었다:

1. **Chain/LCEL 은 한 방향 파이프라인이다** — A 다음 B, B 다음 C 처럼 앞으로만 흐른다 (이런 구조를 **DAG** 라 부른다 — 되돌아가는 길이 없는 그래프). 그런데 에이전트의 본질은 “판단 → 도구 실행 → 결과 보고 다시 판단”을 반복하는 **순환(루프)** 이다. 한 방향 구조로는 표현 불가.
2. **구 AgentExecutor 는 블랙박스였다** — 루프는 돌지만 안이 봉인돼 있어 프롬프트·중단 조건· 중간 상태를 개발자가 손볼 수 없었다. 데모는 쉬운데 실서비스 수준의 커스터마이즈가 불가능했다.
3. **실서비스 요구가 추가됐다** — 실행 중간에 사람 승인 받기(**human-in-the-loop**, 자동 흐름 중간에 사람 확인을 끼워 넣는 것), 서버가 재시작돼도 하던 일을 이어서 하기, 진행 상황을 중간중간 화면에 보여주기, 문제 생긴 실행을 그 시점부터 재현해 보기.

그래서 2024년 1월, “제어 가능한 에이전트 실행 엔진”으로 LangGraph 가 공개됐다. 2025년 10월 LangChain 1.0 과 함께 1.0 정식 버전이 나왔다. LangChain 팀의 공식 역할 정리: **LangGraph = 세밀하게 제어하는 저수준 엔진, LangChain `create_agent` = 그 위의 간편 진입점.**

## 3. 핵심 개념 6개

```python
class State(TypedDict):
    messages: Annotated[list, add_messages]   # ① state + reducer(병합 규칙)
    metadata: dict

graph = StateGraph(State)
graph.add_node("extract", extract_metadata)   # ② node: state 를 받아 변경분을 반환
graph.add_edge(START, "extract")              # ③ edge: 단계 간 연결선
graph.add_conditional_edges("extract", route, ["recommend", "reply"])
app = graph.compile(checkpointer=saver)       # → 실행 가능한 앱 (내부는 Pregel 엔진)
```

| # | 개념              | 풀어서 설명하면                                                                                 | 왜 이게 판매 포인트인가                                |
| - | --------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------- |
| ① | State + reducer | 모든 단계가 공유하는 상태. reducer 는 각 단계의 반환값을 기존 상태에 어떻게 합칠지 정하는 병합 규칙 함수 (예: 메시지는 덮어쓰지 말고 밑에 추가) | 상태 관리 코드를 직접 안 짜도 됨                          |
| ② | Node            | 상태를 받아 일부를 바꿔 돌려주는 보통의 함수                                                                | —                                            |
| ③ | Edge            | 단계와 단계를 잇는 연결선. 조건 분기도, 뒤로 돌아가는 연결도 된다                                                   | **루프를 그릴 수 있다**                              |
| ④ | Checkpointer    | 매 단계마다 상태를 저장소에 기록 — 게임의 세이브 포인트와 같다                                                     | 서버가 죽어도 이어서 실행, 과거 시점으로 되돌려 재실행(time-travel) |
| ⑤ | interrupt       | 실행을 멈춰 놓고 사람 입력을 기다렸다가, 입력이 오면 멈춘 지점부터 재개                                                | 사람 승인 게이트를 깔끔하게 구현                           |
| ⑥ | Send            | 실행 도중 같은 단계를 N개로 복제해 동시 실행(**fan-out**)하고 결과를 모음                                         | 병렬 처리 패턴을 직접 안 짜도 됨                          |

여기에 진행 상황을 실시간으로 밖에 흘려주는 스트리밍 모드 여러 개(`values`/`updates`/`messages`/`custom`)가 있고, 그래프 선언 없이 일반 함수에 데코레이터만 붙여 쓰는 방식(`@entrypoint`/`@task`)도 있다.

## 4. 실행 모델의 실체 — 선언의 대가

`compile()` 이 돌려주는 것은 Google 의 분산 그래프 처리 논문에서 유래한 **Pregel** 방식의 실행 엔진이다. 동작은 라운드 반복이다: 매 라운드(**super-step** 이라 부른다)마다 “지금 실행할 수 있는 단계들을 모아서 → (필요하면 병렬로) 실행하고 → 결과를 상태에 반영”한다.

여기서 눈에 잘 안 보이는 비용이 발생한다:

* **내 코드가 도는 스레드를 프레임워크가 정한다.** 병렬 실행을 위해 자체 스레드 풀 (ThreadPoolExecutor)을 쓰기 때문이다. 심지어 분기 하나 없는 순차 그래프도 특정 설정 (예: 스트리밍 모드 조합)에 따라 별도 스레드에서 실행될 수 있다.
* **스레드마다 따로 보관되는 자원과 충돌할 수 있다.** 예를 들어 Django 의 DB 커넥션은 스레드별로 따로 관리된다(**스레드-로컬**: 스레드마다 다른 스레드에선 안 보이는 전용 보관함). Django 는 “HTTP 요청이 끝나면 그 요청 스레드의 커넥션을 정리한다”고 가정하는데, 프레임워크가 만든 별도 스레드에서 열린 커넥션은 이 정리 로직의 눈에 안 띄어 반납되지 않고 쌓일 수 있다 → 커넥션 풀 고갈로 이어질 수 있는 종류의 문제다.
* 오류 스택트레이스가 엔진 내부를 관통해 디버깅이 어렵고, `graph.stream()` 의 반환 타입이 느슨해 받는 쪽 코드의 타입 검사 효용이 떨어진다.

> **교훈: 그래프 선언이 아무리 단순해 보여도, 구매하는 것은 “실행 엔진 전체”다.** checkpointer 를 안 쓰고 interrupt 를 안 써도 실행 엔진의 복잡성 비용은 전액 청구된다. 프레임워크의 가치는 “내가 실제로 쓰는 기능”에서만 나오고, 비용은 무조건 나간다.

## 5. 무엇을 살 때 가치 있나 — 기능별 체크리스트

도입/유지 판단은 취향이 아니라 **이 표에서 몇 줄에 해당하느냐**로 한다:

| 필요한 것        | 이런 상황이라면                                    | 직접 만들면 얼마나 힘든가                                  |
| ------------ | ------------------------------------------- | ----------------------------------------------- |
| 동적 루프        | LLM 이 도구를 몇 번 부를지 실행 전엔 모른다                 | while 루프로 가능하나 상태·중단 조건 관리가 점점 커짐               |
| Checkpointer | 서버 재시작 후 이어서 실행, 실행 상태를 DB 에 보관, 과거 시점부터 재현 | 매우 힘듦 — 사실상 프레임워크를 재발명하게 됨                      |
| interrupt    | 실행 중간에 사람 승인을 받고 이어서 진행                     | 힘듦 — 상태 저장 + 재개 지점 관리 필요                        |
| Send (병렬 분기) | 작업을 쪼개 동시 실행하고 결과를 합침                       | 중간 — 스레드/비동기 관리 직접                              |
| 멀티에이전트       | 역할이 다른 에이전트끼리 일을 넘기고 돌려받음                   | 힘듦                                              |
| 고정 순차 파이프라인  | 단계와 순서가 코드 작성 시점에 이미 정해져 있음                 | **보통의 함수 호출이 오히려 우월** — 스택 투명, 타입 정확, 스레드 걱정 없음 |

**마지막 줄이 함정이다.** “나중에 에이전트로 키울 거니까”라며 고정 파이프라인에 LangGraph 를 깔면, §4 의 비용은 미리 내면서 이 표의 가치는 하나도 못 받는다.

## 6. 도입·제거 판단 기준

### 도입 신호 (직접 짜던 코드 → LangGraph)

* while 루프 + 상태 dict + 저장/복원 + 재개를 직접 구현하다 보니 사실상 프레임워크를 재발명하고 있다
* 사람 승인 게이트, 오래 도는 작업의 중단/재개, 상태 재현 요구가 로드맵에 실제로 있다
* 역할이 다른 에이전트 간 위임이 2개 이상 생겼다

### 제거 신호 (LangGraph → 직접 짜는 코드)

* 그래프가 사실상 직선이다 — 조건 분기 한두 개뿐, 되돌아가는 순환이 없다
* checkpointer / interrupt / Send / 도구 루프를 하나도 안 쓴다
* 실행 엔진이 내 인프라(DB 커넥션, 스레드 가정 등)와 충돌해 우회 코드가 쌓이고 있다
* 의존성 관리·버전 업그레이드·디버깅에 드는 비용이 쓰는 기능의 가치를 넘었다

### 판단 절차

1. **사용 기능 점검** — §5 표를 놓고 실제 코드가 쓰는 줄만 체크한다 (grep 으로 확인 가능한 사실 문제다)
2. **비용 목록화** — 우회 코드, 타입 구멍, 의존성, 팀원 학습 비용을 적어본다
3. 옮기기로 했다면 **외부에서 보이는 동작(응답 형식, 이벤트 순서)을 먼저 고정**해 놓고 최소로 전환한다. 이때 부품 계층(LangChain 의 모델 클라이언트·메시지 타입)은 별개 결정이므로 함께 걷어낼 이유가 없다

예를 들어 “입력 분석 → (조건부) 검색 → 응답 생성” 세 단계로 고정된 챗봇이라면: 루프도 없고, 저장/재개도 안 쓰고, 사람 승인도 없다 — 이런 경우는 그냥 함수 세 개를 순서대로 부르는 코드가 더 단순하고, 디버깅하기 쉽고, 스레드 문제도 없다.

## 7. 대안 지형 — LangGraph 만 있는 게 아니다

* **프레임워크 없이 직접** — Anthropic 의 “Building Effective Agents”(2024-12) 가 대표 논지: 흐름을 코드가 정하는 **workflow** 와 LLM 이 정하는 **agent** 를 구분하고, 대부분의 문제는 단순한 조합 패턴으로 충분하니 **가장 단순한 구성에서 시작해 필요할 때만 복잡도를 추가**하라. “12-Factor Agents” 도 같은 맥락이다 (“실행 흐름은 네가 소유하라”).
* **LangChain 1.0 `create_agent`** — 표준형 도구 호출 에이전트가 필요하면 가장 빠른 길 (내부는 LangGraph)
* **OpenAI Agents SDK / Google ADK** — 각 프로바이더 진영의 에이전트 프레임워크
* **PydanticAI** — 타입 검사를 중심에 둔 가벼운 대안
* **LlamaIndex Workflows** — 그래프 대신 이벤트 기반 단계 모델
* **CrewAI / Microsoft Agent Framework** — 역할 기반 멀티에이전트 특화

선택 사다리로 요약하면:

```
공식 SDK ──→ LangChain(부품만) ──→ + 실행 흐름은 직접 작성 ──→ + LangGraph ──→ + Platform(배포·영속 인프라)
        오른쪽으로 갈수록 능력이 늘지만 비용(불투명성·종속·업그레이드 부담)도 늘어난다.
        오른쪽으로 가는 유일하게 정당한 이유: §5 표의 기능이 “지금” 필요할 때.
```

## 용어 정리

| 용어                        | 뜻                                                    |
| ------------------------- | ---------------------------------------------------- |
| 오케스트레이션                   | 여러 작업을 어떤 순서·조건·병렬로 실행할지 지휘하는 일                      |
| 에이전트                      | LLM 이 스스로 판단해 도구를 골라 쓰고 다음 행동을 정하는 방식의 프로그램          |
| DAG                       | 한 방향으로만 흐르고 되돌아가는 길이 없는 그래프 = 파이프라인                  |
| 런타임 / 실행 엔진               | 내 코드를 넘겨받아 언제 어디서 실행할지 대신 정하는 엔진 (예: Celery 워커)      |
| super-step                | Pregel 엔진의 한 라운드 — 실행 가능한 단계들을 모아 실행하고 결과를 반영        |
| 스레드-로컬                    | 스레드마다 따로 보관돼 다른 스레드에서는 안 보이는 값 (Django DB 커넥션이 대표 예) |
| checkpointer              | 매 단계마다 상태를 저장해 두는 장치 — 게임 세이브 포인트                    |
| time-travel               | 저장해 둔 과거 시점으로 되돌아가 그때부터 다시 실행해 보는 것                  |
| human-in-the-loop (HITL)  | 자동 실행 중간에 사람 확인/승인을 끼워 넣는 것                          |
| fan-out                   | 하나의 작업을 여러 개로 쪼개 동시에 실행하는 것                          |
| reducer                   | 여러 결과를 기존 상태에 어떻게 합칠지 정하는 병합 규칙 함수                   |
| 내구 실행 (durable execution) | 프로세스가 죽거나 재시작돼도 저장된 상태에서 이어서 실행되는 성질                 |
