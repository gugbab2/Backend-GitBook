# 2.4

### 이력서 v2.4 STAR 복습 가이드

2026년 11월 18일 기준 · 면접 준비용

이력서 v2.4와 이전 이력서, v2.2 해설지, 확인 가능한 Jira 기록을 대조해 복원한 자료다. 법틀은 개발 기록과 확인된 반영 단계, 쿠콘은 이력서와 당시 설명에 남아 있는 역할·성과를 기준으로 적었다. 예전 성과의 산정 근거와 정확한 구현 선택은 각 사례의 확인 항목에 남겼다.

#### 자료 구성

* **법틀 STAR 사례** - 계약 기안 출시, 의사결정 전 검토, LLM 비교, SSE, 요청별 결과 복구, 조회 장애 대응, 법령 갱신
* **쿠콘 STAR 사례** - 정산 검증, 1원 계좌 검증의 상태 보정과 거래 지연 개선, 엑셀, 파일 대사, 분할 커밋

#### 먼저 익혀 둘 답변

> 금융 백엔드와 업무용 AI 에이전트를 개발해 온 4년 차 개발자입니다. 금융 서비스에선 거래와 정산 결과를 확인하고, 요청이 몰려도 거래 처리가 지연되지 않도록 개선했습니다. 법틀에서는 대화형 계약 기안 에이전트를 기존 법무 시스템에 연결해 고객사에 공동 출시했고, 실무자가 결정을 내리기 전에 AI의 검토 의견과 원문 근거를 확인하는 기능을 개발했습니다. 앞으로도 사용자가 AI 결과를 확인하고 실제 판단에 활용할 수 있는 업무 시스템을 만들고 싶습니다.

#### STAR로 답하는 법

| 단계     | 한 문장으로 답할 질문             | 면접에서 꺼낼 내용                           |
| ------ | ------------------------ | ------------------------------------ |
| S · 상황 | 사용자가 무엇 때문에 불편했나?        | 사용자와 기존 흐름, 실패가 드러난 지점               |
| T · 과제 | 팀 목표 중 내가 맡은 범위는 어디까지였나? | 직접 구현한 부분, 협업 지점, 지켜야 한 제약           |
| A · 행동 | 원인을 어떻게 확인했고 무엇을 선택했나?   | 관찰 근거 하나, 설계 선택 하나, 처리 순서            |
| R · 결과 | 어떤 근거로 어디까지 결과를 말할 수 있나? | 공동 출시, 브랜치 반영, 기능 개발, 정량 지표 중 확인된 범위 |

처음에는 사례당 60\~90초를 목표로 상황과 역할을 짧게 말한다. 이어 “왜 그렇게 구현했나요?”라는 질문에는 다른 선택지와 그때 고려한 기준을 답한다. 실제로 비교했던 선택과 지금이라면 검토할 대안을 구분해 두면 기억이 흐릿해도 설명을 이어갈 수 있다.

#### 복습할 때 남길 메모

* 사례마다 “내가 직접 바꾼 것”을 동사 세 개로 적는다.
* 먼저 그림을 그린다. 입력 → 상태 변화 → 결과 소비 지점 → 실패 시 복구 경로만 적어도 흐름이 떠오른다.
* 수치나 설정값이 기억나면 근거를 찾아 날짜와 함께 기록한다. 수치가 가물가물한 상태에선 적용 범위와 바뀐 동작부터 설명한다.
* 출시 후 개선에 대해 질문받으면 경험과 다음에 검증하고 싶은 항목을 나눠 말한다. 에이전트라면 검토 의견의 채택·미반영 사유와 근거 불일치 유형, 금융 배치라면 예외 건과 재처리 결과가 검증의 출발점이 된다.

### 금융권 AI 에이전트 면접 꼬리 질문 답변

먼저 실제 경험을 한두 문장으로 답한다. 개선 설계까지 물으면 “지금 같은 문제를 맡는다면”으로 시점을 바꿔 답한다.

#### 정산 검증과 중복 이체·출금

**질문** - 결제 상태는 성공인데 정산 금액이 다르면 어떤 조건에서 이체·출금 대상으로 넘어가나요? 배치를 다시 실행하면 같은 건을 두 번 넘길 수 있나요?

**실제로 한 일**

> 응답을 받지 못한 결제는 먼저 기존 거래의 상태를 재조회했습니다. 결제사 기록과 내부 정산 데이터를 대조해서 검증된 금액을 후속 이체·출금에 쓸 수 있게 하는 배치를 개발했습니다. 제 업무는 배치 개발까지였고, 당시 불일치 건의 후속 처리나 중복 이체 방지 규칙은 확인이 필요합니다.

**지금이라면 이렇게 설계**

> 결제 성공과 정산 확정을 별도 상태로 두겠습니다. 같은 거래의 기준일과 통화, 취소·환불을 반영한 정산 금액이 일치할 때만 후속 처리 대상으로 넘깁니다. 금액이 다르면 보류하고 차이와 판단 이유를 남긴 뒤 재대사합니다. 지급 건마다 고정 식별자를 두고 상태 전이와 전송 대상 기록을 같은 트랜잭션으로 저장하겠습니다. 전송이 타임아웃되면 같은 식별자로 외부 처리 여부를 먼저 확인하고, 재전송이 필요할 때도 같은 식별자를 씁니다.

외부가 중복 방지 키를 지원하면 같은 키에 대한 재시도가 같은 지급 건으로 묶이도록 합니다. 그 기능과 확정 상태 조회가 모두 없다면 결과가 불명확한 송금은 자동 재전송하지 않고 확인 대상으로 보냅니다. 내부에서 한 번만 처리하도록 막는 것과 외부에서 돈이 한 번만 움직이는 것을 보장하는 범위가 다르기 때문입니다.

**기록 미확인** - 실제 매칭 키, 정산액 확정과 불일치 보류 조건, 검증 결과를 넘긴 방식, 재실행·중복 방지 구현과 운영 여부.

#### 1원 계좌 검증의 두 지표와 늦은 은행 응답

**질문** - 95% 두 개의 분자·분모와 기간은 각각 무엇인가요? 늦은 은행 응답과 배치 보정이 엇갈리면 어느 상태를 적용하나요?

**실제로 한 일**

> 은행 응답이 늦어 내부에 ‘처리 중’으로 남은 거래는 재조회 조건과 배치 주기를 조정해 보정했습니다. 요청이 몰릴 때 거래를 늦추던 실시간 집계는 일 단위 배치로 분리했습니다. 이전 이력서에는 상태 정합성 오류와 거래 지연율이 각각 95% 이상 감소했다고 적혀 있습니다. 현재 확인한 기록에는 두 수치의 산정 기준과 전후 값을 계산할 원집계가 없습니다.

**지금이라면 이렇게 설계**

> 상태 정합성은 정해진 유예 시간이 지난 뒤 은행의 확정 상태를 확인할 수 있는 거래 중 내부 상태가 어긋난 비율로 보겠습니다. 은행에서도 끝까지 결과가 확인되지 않은 건은 별도로 집계합니다. 거래 지연율은 같은 처리 시간 기준을 넘긴 거래를 전체 대상 거래로 나눠, 거래량과 비교 기간을 맞춰 보겠습니다. 갱신 시에는 늦게 도착한 중간 상태가 이미 확인한 최종 상태를 되돌리지 못하게 하고, 서로 다른 최종 상태를 받으면 은행에 다시 조회하겠습니다.

감소율을 설명할 때는 전후 값과 계산에 포함한 거래를 함께 말합니다. 개선 전후 비율을 비교한다면 초기 비율 대비 상대 감소율과 퍼센트포인트 차이를 구분합니다. 콜백과 배치가 동시에 들어오는 경우에는 동일 거래의 허용된 상태 전이만 조건부 갱신으로 반영합니다.

**기록 미확인** - 95%의 원집계와 현재 이력서 수치가 건수인지 비율인지에 대한 원정의, 지연 기준과 비교 기간, 실제 콜백·재조회 결과의 우선순위 및 재시도 상한.

#### AI 검토 품질과 모델 출시 기준

**질문** - 근거가 원문에 있어도 해석이 틀리거나 중요한 위험을 놓치면 어떻게 찾나요? 후보 모델을 언제 운영에 올리겠습니까?

**실제로 한 일**

> 계약서 원문에 인용한 구절이 있는지 확인하고, 근거가 맞지 않는 항목은 제외했습니다. 실무자는 남은 의견과 조항을 확인해 반영 여부를 결정할 수 있었습니다. 초기 모델 비교는 같은 조건의 완료 기록 93쌍에서 필수 항목 탐지, 오탐, 속도, 비용을 본 실험이었습니다. 기존 응답 186개를 다시 처리한 검증은 후처리 회귀를 확인한 결과입니다.

**지금이라면 이렇게 설계**

> 먼저 현업 검토자와 계약 유형마다 반드시 짚어야 할 위험, 허용 가능한 표현, 지적하면 안 되는 항목을 정하겠습니다. 원문 대조로 확인할 수 있는 건 인용 위치이고, 해석의 타당성과 누락 여부는 문서 전체를 기준으로 평가하겠습니다. 중요한 위험 누락이나 근거 없는 금액·날짜 제안을 출시 차단 항목으로 정하고, 합의한 평가를 통과한 후보끼리 응답시간과 비용을 비교하겠습니다. 제한된 트래픽에서 사람이 결과를 확인해 중대 오류가 나오면 배포를 멈추겠습니다.

평가에는 보완할 항목이 없는 계약과, 겉보기엔 비슷하지만 예외 조항 때문에 결론이 달라지는 계약을 함께 넣습니다. 타임아웃이나 근거 필터에서 전부 제외된 결과는 정상적인 ‘지적 없음’과 별도로 집계합니다. 모델 간 비교에는 실패와 재시도를 포함한 처리 시간을 함께 봅니다.

**기록 미확인** - 운영 투입과 최종 합격 기준, 최신 모델·프롬프트·후처리 조합에서 현업이 평가한 중대 위험 누락률, 운영 지연과 실제 청구 비용.

#### 고객사 출시 후 피드백과 개선

**질문** - 고객사가 실제로 어느 단계까지 썼나요? 피드백 하나를 개발에 반영하고 개선 효과를 확인한 사례가 있나요?

**실제로 한 일**

> 팀과 함께 기업 고객 두 곳에 대화형 계약 기안 기능을 출시했습니다. 제가 맡은 부분은 대화와 첨부 문맥 복원, 기존 계약 양식 연동이었습니다. 고객이 어느 단계까지 기능을 썼는지, 피드백을 받아 기능을 바꾼 뒤 지표가 어떻게 변했는지는 확인된 기록이 없습니다.

**지금이라면 이렇게 설계**

> 출시 전에 대화 시작, 양식 열기, 초안 저장, 정식 검토 요청 중 어디에서 시간이 줄어야 하는지부터 정하겠습니다. 단계별 진행률과 소요 시간을 보면서 막히는 구간을 고르고, 실제 사용자에게 이유를 확인하겠습니다. 예를 들어 양식을 연 뒤 저장이 줄어든 이유가 특정 계약 정보의 잘못된 자동 입력이라면, 그 필드의 입력 규칙을 바꾸고 비슷한 계약군에서 재수정 횟수와 작성 시간을 비교하겠습니다.

계약 원문과 개인 식별 정보를 분석용 로그에 남기지 않고 상태·소요 시간·오류 유형을 수집합니다. 사용자가 의견을 많이 반영하더라도 그대로 품질 향상으로 해석하기 어려우므로, 주요 오류와 미반영 이유를 표본으로 확인합니다. 위의 자동 입력 예시는 앞으로의 검증 설계입니다.

**기록 미확인** - 고객사별 사용 단계, 채택률과 작성 시간의 변화, 출시 후 사용자 피드백을 반영하고 효과를 다시 측정한 사례.

#### 조회 만료와 AI 작업의 중복 실행 비용

**질문** - 화면에서 첫 작업은 만료됐는데 AI 서버가 아직 실행 중이면, 재요청 결과와 모델 비용을 각각 어떻게 제어하나요?

**실제로 한 일**

> 기본 경로에선 대기 상한 이후 일시 조회 오류가 세 번째 발생하면 화면에서 작업을 만료해 재실행할 수 있게 했습니다. 상한이 지나도 끝난 결과를 먼저 읽어 봤고, 이전 실행의 응답은 작업 ID와 실행 토큰을 비교해 새 결과를 덮어쓰지 않게 했습니다. 원격 AI 작업이 실제로 취소됐는지, 재요청으로 모델 호출 비용이 중복되는 것까지 막았는지는 확인되지 않았습니다.

**지금이라면 이렇게 설계**

> 같은 실행을 복구하는 재요청에는 처음과 같은 요청 ID를 쓰고, 이미 접수된 작업이나 완료 결과를 반환하겠습니다. 문서 수정이나 의도적인 재분석은 새 실행으로 구분하겠습니다. AI 서버에서 요청 ID를 기준으로 작업을 한 번 등록하고, 워커가 모델을 호출하기 전에 실행을 한 번만 맡도록 상태를 조건부로 바꾸겠습니다. 원격 취소가 가능하면 취소 확인을 받아 상태를 정리하고, 실행 중 취소가 어렵다면 동일 작업을 바로 중복 호출하지 않도록 하겠습니다.

화면에서 결과가 무시되는 것과 모델이 실행되지 않아 비용이 발생하지 않는 것은 서로 다른 결과입니다. 대기 중 취소, 실행 중 취소 요청, 이미 완료된 작업을 상태로 구분합니다. 모델이 응답한 직후 결과 저장이 실패했다면 외부 호출의 확정 여부에 따라 재실행 비용이 남을 수 있습니다. 실행 ID별 모델 호출 횟수와 중복 비용을 따로 관찰합니다.

**기록 미확인** - 당시 AI 서버의 작업 취소와 취소 확인, 모델 호출 전 중복 방지, 운영 재실행률과 중복 청구 규모.

**내가 내린 판단** - 현재 질문을 이전 메시지 목록에서 분리해 중복 입력을 피하고, 이미 추출한 첨부 원문을 다시 써서 후속 질문마다 원본 파일을 새로 보내지 않도록 했다. 추천 양식으로 들어갈 때는 기존 계약 재생성에서 쓰던 필드 채우기 방식을 활용했다. 대화 화면 안에서 기존 입력 폼이 값을 채우고 생성 완료나 취소를 대화 화면으로 알려주는 구조로 연동했다.

**실패 시 처리** - 지원하지 않는 첨부 형식이나 파싱 실패는 요청 오류로 반환했다. 일시적인 모델 연결·호출 한도 오류에는 초기 모델 호출 공통 경로에서 간격을 늘려 재시도하도록 했다. 자동 입력 기능을 사용할 수 없으면 빈 계약 양식으로 작성할 수 있게 했고, 양식 화면 자체를 열지 못한 경우 패널을 닫고 오류를 안내했다.

#### 2. 계약 의사결정 전 AI 검토와 업무 흐름 연동

* **S · 상황** - 실무자가 계약안을 수정하거나 정식 검토에 넘기기 전에 AI에 검토 의견 초안을 요청할 수 있어야 했다. 원문 근거를 확인할 수 있어야 판단에 쓸 수 있고, 이후 계약이 바뀌면 기존 의견이 최신 계약에도 유효하다고 오해할 수 있었다.
* **T · 과제** - 기존 계약 화면 안에 검토 실행과 결과 확인을 연결했다. 내 작업 기록에는 AI 검토 API, 원문 근거 연동, 중복 요청과 계약 변경 처리, 검토 요청으로 판단 맥락을 전달하는 구현이 남아 있다.
* **A · 행동** - 검토를 비동기로 접수하고 실행 당시 계약 입력과 적용 기준을 고정했다. 의견마다 인용 근거를 원문에서 찾아 구절별로 표시하고, 확인한 내용과 AI 의견을 반영하지 않은 사유가 이후 정식 검토 요청으로 이어지게 했다.
* **R · 결과** - 실무자가 기존 업무 화면에서 AI 의견을 요청하고, 근거를 확인한 뒤 자신의 판단과 함께 정식 검토로 넘길 수 있는 흐름을 구현했다. 11월 17일 기준 관련 코드가 기준 브랜치에 반영됐다.

**내가 내린 판단**

* **잘못된 근거가 표시되는 위험을 낮췄다.** 떨어진 근거 문장을 한 문자열로 찾으면 원문 위치나 편집 대상 조항이 잘못 연결될 수 있었다. 기존 공통 대조 로직을 이어받아 구절 목록을 화면에 전달했고, 일부 근거만 맞는 경우를 검토해 구절 하나라도 불일치하면 항목 전체를 제외하는 규칙을 유지했다. 구절이 원문에 있다는 사실은 인용 위치를 확인해 주며, 의견의 타당성은 실무자가 판단한다.
* **검토 결과는 그때 검토한 계약에 연결했다.** 같은 값을 다시 저장하면 결과를 유지했다. 계약 정보·본문·파일이 실제로 달라지면 현재 결과만 무효화하고 당시 결과와 사용자 판단은 읽기 전용 이력에 보존했다. 정식 검토자는 이전 의견을 왜 반영했거나 반영하지 않았는지 이어서 확인할 수 있다.

**실패 시 처리**

* 같은 계약에서 중복으로 실행하거나 상태 변경이 겹치면 잠금 안에서 상태를 다시 확인했다. 이미 새 실행이 시작됐거나 현재 상태가 바뀐 뒤 도착한 이전 응답은 현재 결과를 바꾸지 않도록 처리했다.
* 정상적으로 보완 항목이 0건인 결과, 근거 불일치로 제외한 결과, 작업 실패·만료를 구분했다. 화면에서 편집할 조항을 확정할 수 없으면 위치 확인이 필요하다고 안내하고 조항 편집을 열지 않았다.
* 검토 결과 조회에 일시 오류가 계속되면 기다리는 간격을 늘리고, 허용 시간이 지난 뒤 반복 실패한 작업을 만료해 실무자가 다시 실행할 수 있게 했다. 앱의 만료와 원격 작업 취소의 경계는 별도 사례인 조회 장애 대응에서 설명한다.

**검증 근거**

* **AI 처리 경로** - Jira에 Django 테스트 1,553건 통과와 로컬 HTTP 접수 → 워커 처리 → 결과 조회 검증이 기록됐다. 외부 모델 응답과 큐 등록을 대체해 검증한 범위다.
* **근거와 화면** - 단일·다중 구절, 일부 불일치, 중복 위치를 확인했고, 합성 결과로 다른 요청자의 조회가 거부되는 경우와 구절별 화면 표시를 확인했다. 통합 화면 QA 기록은 85개 중 77개 실행, 72개 통과, 5개 불일치였고 이후 로컬 실제 화면 QA에서 빈 조항 저장 차단 등 수정 3건의 동작을 확인했다. 최종 통합 QA 결과와 구분한다.

**기록 미확인** - 전체 화면과 실모델·실문서 편집·알림을 함께 검증한 최종 통합 결과, 운영 배포와 사용성 성과, 출시 후 실제 피드백은 확인되지 않았다. 팀 정책 합의를 본인이 단독 결정한 범위도 기록으로 구분되지 않는다.

**60초 답변 예시**

> 실무자가 계약 관련 결정을 내리기 전에 AI 의견과 그 근거를 확인하는 흐름을 개발했습니다. 제가 맡은 부분에서 근거를 구절별로 원문과 대조하고, 이어지는 화면에서는 편집 대상이 명확한 경우에만 해당 조항을 다룰 수 있게 했습니다. 계약이 실제로 바뀌면 현재 결과를 무효화하되 당시 결과와 사용자 판단은 이력으로 남겼습니다. 로컬에선 작업 접수부터 결과 조회까지 확인했고, 실제 운영 적용과 전체 통합 검증은 별도로 확인해야 합니다.

**돌아볼 기록** - 초안 검토 API 구현과 회귀 테스트, 근거 구절 목록 전환, 실행·상태 조회, 계약 변경·검토 요청 연동, 화면 QA 및 통합 현황

#### 3. 기능별 LLM 후보 비교와 적용 판단

* **S · 상황** - 업무에서 필요한 지적을 찾아도 불필요한 경고가 많거나 응답이 늦고 비용이 높으면 쓰기 어렵다. 계약 검토 기능에 넣을 모델을 비교해야 했다.

#### 4. SSE 실시간 응답과 DB 연결 누수 개선

* **S · 상황** - 스테이징에서 AI 실시간 응답이 약 120초 동안 멈췄다가 끊겼다. 애플리케이션에는 DB 연결 오류가 남았고, 그 시각에 연결 풀에서도 쿼리 대기가 끝나며 연결이 종료됐다.
* **T · 과제** - 스트리밍 단절이 어디에서 시작됐는지 찾고, 문제가 생긴 연결의 소유 스레드에서 안전하게 반환되도록 수정했다.
* **A · 행동** - 업무 서버의 읽기 타임아웃, AI 서버의 DB 오류, 연결 풀의 오래된 연결과 대기 로그를 대조했다. 노드가 DB 연결을 연 스레드와 요청 처리 스레드가 다르다는 점을 로컬에서 관측하고, 노드가 끝나는 지점으로 연결 정리를 옮겼다.
* **R · 결과** - 노드에서 사용한 연결이 실행 직후 닫히는 것을 로컬에서 확인했다. 확인된 연결 누수 경로의 수정과 운영 단절률 변화는 구분한다.

**내가 내린 판단**

* 처음에는 스트림이 끝날 때 요청 스레드에서 정리하는 방안을 검토했다. 스레드 확인 결과, 모델 설정 조회와 토큰 사용량 기록은 LangGraph 워커에서 DB 연결을 열었다. Django 연결은 스레드별로 관리되므로 요청 종료 시점의 정리는 이 연결에 닿지 않았다. 배포 전 이 접근을 접고 **연결을 연 워커의 노드 종료 시점**에 반환하도록 바꿨다.
* 해당 환경의 세션 방식 연결 풀에서는 남은 클라이언트 연결이 서버 연결을 계속 점유했다. 타임아웃 120초는 대기가 드러난 지점으로, 연결 풀에서 사용 가능한 슬롯이 줄어드는 원인부터 수정했다.

**실패 시 처리**

* 노드가 정상 종료하거나 예외가 나도 종료 처리에서 연결 정리를 시도했다. 열린 트랜잭션 안에서는 연결을 닫지 않았고, 정리 자체에서 오류가 나도 원래 성공 결과나 기존 실행 오류를 가리지 않도록 했다.
* 스트리밍 요청 스레드가 DB 연결을 오래 점유하는 현상은 별도 후속 작업으로 기록됐다. 당시 내 수정 범위는 워커에서 사용하고도 반환되지 않던 연결이었다.

**검증 근거**

* **변경 전** - 애플리케이션 오류와 연결 풀 대기 종료 시각이 거의 일치했고, 오래 남은 연결이 애플리케이션 쪽에서 반복 누적되는 것을 확인했다.
* **변경 후** - 로컬에서 요청과 노드가 서로 다른 스레드에서 실행되고, 노드가 실제 DB 연결을 열었다가 종료 직후 닫는 것을 관측했다. 성공·예외·정리 실패·트랜잭션 보호 회귀 테스트가 추가됐고, 당시 컨테이너 Django 테스트 461건 통과가 작업 기록에 남아 있다.

**기록 미확인** - 수정 배포 후 같은 조건에서 연결 누적 증가율, SSE 단절률, 첫 응답 시간, 피크 동시 연결 수를 전후 비교한 결과는 확인되지 않았다.

**60초 답변 예시**

> 답변이 120초 동안 오지 않다가 연결이 끊겼습니다. 애플리케이션과 DB 연결 풀 로그를 대조하고, 누가 그 연결을 열었는지 스레드를 추적했습니다. 처음 검토한 요청 종료 정리는 워커의 연결에는 닿지 않았습니다. 워커가 자기 노드를 끝낼 때 반환하도록 바꾸고 열린 트랜잭션은 보호했습니다. 로컬에서 실제 연결이 열렸다가 닫히는 것과 예외 경로를 확인했습니다.

#### 5. 비동기 검토 재요청에서 동일 요청의 결과 복구

* **S · 상황** - 같은 대화에서 여러 번 문서를 분석할 수 있게 되면서 대화당 이력 한 줄로는 각 결과를 구분할 수 없었다. 응답 도중 연결이 끊기면 AI는 이미 실행 중인데 업무 서버에선 실패로 보여 재전송 때 이력이 중복되거나 다른 분석 결과가 붙을 수 있었다.
* **T · 과제** - 분석마다 이력을 남기고, 접수 응답을 못 받아 같은 요청을 다시 보낼 때 그 요청의 이력과 결과를 정확히 찾도록 했다.
* **A · 행동** - 업무 서버 이력에 브라우저가 만든 요청 ID를 저장하고 사용자와 요청 ID의 조합에 DB 유일성 제약을 적용했다. 같은 사용자의 같은 대화에서 같은 ID로 들어오면 기존 이력을 재사용하고, 단절 후 결과를 찾을 때도 같은 ID의 분석만 연결했다.
* **R · 결과** - 한 대화에서 여러 분석을 따로 조회할 수 있게 했고, 같은 요청의 재전송과 인접 분석 결과가 서로 섞이는 문제를 막는 처리를 구현했다.

**내가 내린 판단** - 가까운 시각이나 대화의 최신 이력으로 결과를 고르던 방식은 연속 요청에 취약했다. 재전송에서도 같은 값을 알아야 하므로 브라우저와 AI 서버가 이미 쓰는 요청 ID를 업무 서버가 함께 보관하도록 했다. 먼저 조회해서 없으면 삽입하는 방법의 경쟁 조건은 DB 제약에서 판정하고, 충돌하면 먼저 만들어진 행을 조회해 재사용했다.

**실패 시 처리**

* 동시 생성에서 밀린 요청은 기존 행을 볼 수 있어도 상태를 바꿀 권한은 갖지 않게 했다. 먼저 처리 중인 요청을 뒤늦은 오류가 실패로 덮는 경우를 막았다. 순차 재전송에서는 같은 대화의 실패 행만 대기로 되돌렸고 완료 행은 보존했다.
* 다른 대화에 속한 ID는 거절했다. 이미 회수한 이력의 키는 해제해 정상 재시도가 막히지 않게 했다. 요청 ID가 있는 행은 일치 결과가 없으면 기다리거나 로그로 관측했다. 시각을 쓰는 방식은 ID가 없는 이전 데이터에만 남겼다.

**검증 근거** - 변경 기록에 로컬 DB 검증 스크립트의 행 생성·재전송 37건, 동시 생성 경합 10건, 대화 소속 검사 5건, 단절 수습 21건 통과가 기록돼 있다. 연속 두 요청이 모두 끊겼을 때 각자 자기 결과를 받는 경우와, 화면에서 두 분석이 별도 이력으로 보이고 재전송 시 한 줄로 남는 경우도 확인했다.

**기록 미확인** - 브라우저를 실제로 닫은 뒤 배치가 결과를 이어 받는 전체 경로는 변경 기록의 남은 검증 항목이다. 운영 중복·오연결률과 전체 AI 실행 횟수의 보장 범위도 재확인이 필요하다. 이전 명세의 시각 창 설명과 최종 병합 기록이 다를 때는 키가 있는 행의 동작을 최종 변경 기록 기준으로 설명한다.

**60초 답변 예시**

> 접수 응답을 받지 못해도 AI 쪽에서는 이미 분석 중일 수 있었습니다. 그래서 브라우저가 만든 요청 ID를 업무 서버 이력에도 저장하고, 같은 사용자의 같은 요청이 동시에 와도 DB가 한 행만 허용하게 했습니다. 충돌한 요청은 기존 행을 재사용하되 상태를 바꿀 수 없게 했고, 연결이 끊긴 뒤에는 그 ID와 일치하는 결과만 복구했습니다. 연속 단절과 동시 재전송을 로컬 DB에서 검증했습니다.

**돌아볼 기록** - 분석 단위 이력 Jira, 병합 변경의 구현·테스트 계획, 서버 간 API 설계 회고, v2.2·v2.3 이력서

#### 6. 결과 조회 장애가 이어질 때 재실행 경로 마련

* **S · 상황** - 계약 사전 점검에서 결과 조회가 502나 타임아웃으로 계속 실패하면 화면에 ‘진행 중’이 남고 재실행도 막혔다. 반대로 조회 오류 한 번에 만료하면 이미 끝났을 결과를 버릴 수 있었다.
* **T · 과제** - 조회 장애로 진행이 멈춘 작업을 정리하고, 완료 결과를 받을 기회를 유지하면서 사용자가 다시 요청할 수 있게 했다.
* **A · 행동** - 계약 사전 점검의 대기 상한과 결과 조회 응답 대기를 조정했다. 화면 조회 간격을 단계적으로 늘리고, 대기 상한이 지나도 결과를 먼저 읽어 본 뒤 시간 초과 여부를 판단했다.
* **R · 결과** - 지속적인 조회 장애가 발생하는 계약 사전 점검에서 시간 초과 안내와 재실행 경로를 구현했다. 리뷰를 반영해 11월 17일 기준 브랜치에 반영했다.

**내가 내린 판단** - AI 큐 대기와 실행 한도를 합쳐 약 5분인 점을 기준으로 사용자 대기 상한을 10분으로 잡았다. 상한 이후 단 한 번의 통신 실패만으로 닫는 초기 방안은 이미 생성된 결과까지 놓칠 수 있어, 리뷰를 반영해 실행별 일시 오류 횟수를 세고 3번째 실패에서 닫도록 수정했다. 화면 조회를 최대 30초 간격까지 늦추고 이 조회의 응답 대기만 짧게 설정했다.

### 쿠콘 STAR 사례

결제·정산 배치는 후속 이체·출금에 쓸 금액을 검증했다. 1원 계좌 검증은 같은 서비스의 두 문제인 거래 상태 미확정과 요청 집중 시 거래 지연을 각각 다뤘다. 결제 중계의 파일 대사와 가맹점 정보 갱신은 별도 작업이다.

#### 1. 검증된 정산 금액으로 이체·출금할 수 있도록 배치 개발

* **S · 상황** - 상품권 결제에서 외부 응답이 늦으면 결제 결과가 미확정으로 남을 수 있었다. 결제사 기록과 내부 정산 데이터가 맞는지 확인해야 후속 이체·출금에 어느 금액을 써야 하는지 판단할 수 있었다.
* **T · 과제** - 미확정 결제를 다시 확인하고, 결제사 기록과 내부 정산 데이터를 대조해 검증된 금액을 후속 처리에 쓸 수 있도록 배치를 개발했다.
* **A · 행동** - 미확정 거래의 상태를 재조회하고, 결제사 쪽 기록과 내부 정산 데이터를 비교해 결과와 금액을 확인하는 흐름을 구현했다.
* **R · 결과** - 검증된 정산 금액으로 이체·출금할 수 있는 흐름을 개발했다. 내가 맡은 범위는 배치 개발까지였다. 개발을 마치고 퇴사했으며, 후속 이체·출금 운영은 직접 담당하지 않았다.

**내가 내린 판단**

* 타임아웃은 결과를 받지 못한 상태다. 이미 결제사가 처리했을 수 있으므로 결제를 다시 요청하기 전에 기존 거래의 상태를 확인하도록 구현했다. 이때 상태 재확인은 거래가 어떻게 처리됐는지를, 데이터 대조는 후속 처리에 쓸 금액을 확인하는 단계였다.

**실패 시 처리**

* 최초 응답만으로 결과가 확정되지 않은 거래는 재조회 경로에서 다뤘다. 외부와 내부 정산 기록의 차이를 찾도록 검증을 넣었다. 자동 보류·보정·재처리 중 불일치 건에 어떤 후속 동작을 적용했는지는 당시 기록에서 확인되지 않았다. 면접에서 “차이를 찾은 뒤 금액을 임의로 바꿨는가”라는 질문을 받으면, 확인된 대조 기능과 실제 운영 범위를 먼저 설명한다.
* 설계 질문으로 중복 이체를 묻는다면, 거래 식별자와 실행 이력으로 상태를 확인한 뒤 재시도하는 방안을 설명할 수 있다. 이 경우 실제 당시 배치의 멱등성 구현 여부는 별도로 확인할 부분이다.

**검증 근거** - v2.2·v2.3 이력서와 v2.2 해설지에 미확정 거래 재조회와 정산 데이터 대조가 기록돼 있다. 후속 이체·출금에 검증된 금액을 쓸 수 있게 했다는 결과와 개발 후 퇴사한 범위는 본인이 확인한 내용이다. 접근 가능한 Jira는 법틀 기록이어서 쿠콘 배치의 테스트·운영 근거는 확인되지 않았다.

**기록 미확인** - 대조 키, 취소·부분 환불과 금액 불일치 조건, 재조회 종료 기준, 검증 결과를 후속 이체·출금으로 전달한 형태, 중복 실행 방지, 테스트 케이스와 운영 반영 여부. 별도의 결제 중계 파일 대사·SMS 알림 기록은 이 배치의 검증 근거로 사용하지 않는다.

#### 2. 1원 계좌 검증의 미확정 거래 상태 보정

* **S · 상황** - 1원 계좌 검증을 요청한 뒤 은행 응답이 늦으면 외부에서 처리가 끝났더라도 내부 거래가 ‘처리 중’에 남을 수 있었다.

* **R · 결과** - 이전 이력서는 상태 정합성 오류가 95% 이상 감소했다고 기록한다. 원집계에서 재계산한 수치는 확보하지 못했다.

**실패 시 처리** - 은행 응답이 없어 결과가 미확정인 거래를 상태 재조회로 보정했다. 다시 조회해도 미확정이거나 외부 오류가 계속됐을 때의 재조회 상한, 늦은 콜백과 배치 결과가 겹칠 때 적용한 우선순위는 확인되지 않았다. 이 부분을 질문받으면 재조회로 결과를 확인하는 흐름까지를 실제 경험으로 설명한다.

**실패 시 처리** - 분할 커밋을 하면 뒤의 묶음이 실패해도 이미 커밋한 묶음이 남을 수 있다. 그래서 면접에서 중간 실패가 질문되면 확정 범위, 재개 위치, 같은 가맹점 정보를 다시 처리해도 되는 조건을 설명해야 한다. 당시 배치의 정확한 재개·롤백·중복 방어는 기록에서 확인되지 않았다.

**검증 근거** - 초기와 후기 이력서 모두 1,000건 단위 커밋과 1분 이내를 남겼다. 30분이라는 기준과 약 30만 건은 초기 기록에만 묶여 있고, 후기 기록의 일 50만 건과 같은 배치 실행을 다시 측정했는지는 확인되지 않았다.

**기록 미확인** - 1회 실행량과 일 물량의 관계, 비교에 사용한 데이터·DB·부하 조건, 측정에 조회·외부 전달이 포함됐는지, 1,000건 선택과 재실행 방법. 정확한 쿼리와 측정 근거가 확인될 때만 시간복잡도나 특정 DB 병목을 원인으로 설명한다.

**45초 답변 예시**

> 가맹점 정보를 한꺼번에 갱신하는 배치가 오래 걸려 트랜잭션 단위를 1,000건씩으로 변경했습니다. 초기 이력서에는 약 30만 건을 처리할 때 30분에서 1분 이내로 줄였다고 기록돼 있습니다. 후기 문서의 일 처리량은 별도 표기로 남아 있어, 면접에서는 제가 바꾼 커밋 경계와 측정 범위를 구분해 설명합니다.

**돌아볼 기록** - v1.0·v1.1의 30만 건·개선 전후 시간, v1.4·v2.3의 일 처리량, v2.2 해설지의 측정 범위 확인 항목

#### 기술 복습 메모

| 질문                          | 답변에서 설명할 원리                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------ |
| 결과가 미확정이면 다시 결제하면 되나?       | 첫 거래가 외부에서 완료됐을 수 있다. 재조회로 상태를 먼저 확인하고, 재실행이 필요하다면 거래 식별과 멱등성 보장 범위를 함께 확인한다.              |
| 정산 검증과 파일 대사는 어떻게 다르나?      | 여기서 정산 검증은 후속 이체·출금에 쓸 금액을 검증하는 흐름이다. 파일 대사는 외부와 내부 기록의 차이를 찾아 담당자가 확인하도록 전달하는 흐름이다.       |
| 실시간 집계를 일 배치로 옮길 때 무엇을 바꾸나? | 요청 경로의 집계 쓰기를 없애면 잠금 경합을 줄일 수 있다. 집계 최신성은 낮아지므로 얼마나 늦어도 되는지와 배치가 실패했을 때 재처리 기준을 같이 봐야 한다.  |
| 엑셀 처리에는 왜 두 가지 최적화가 필요한가?   | DB에서 한 번에 읽는 행 수와 엑셀 작성기가 보관하는 행 수는 별개의 메모리 사용 원인이다. 조회와 파일 생성을 각각 제한하고 임시 파일·디스크 비용도 살핀다. |
| 분할 커밋은 어떤 복구를 요구하나?         | 일부 구간이 이미 커밋된 상태에서 후속 구간이 실패할 수 있다. 재실행 기준과 이미 반영된 구간에서 일어나는 중복 갱신을 통제해야 한다.               |
