# 2.4

### 이력서 v2.4 STAR 복습 가이드

2026년 11월 18일 기준 · 면접 준비용

이력서 v2.4와 이전 이력서, v2.2 해설지, 확인 가능한 Jira 기록을 대조해 복원한 자료다. 법틀은 개발 기록과 확인된 반영 단계, 쿠콘은 이력서와 당시 설명에 남아 있는 역할·성과를 기준으로 적었다. 예전 성과의 산정 근거와 정확한 구현 선택은 각 사례의 확인 항목에 남겼다.

#### 자료 구성

* **법틀 STAR 사례** - 계약 기안 출시, 의사결정 전 검토, LLM 비교, SSE, 요청별 결과 복구, 조회 장애 대응, 법령 갱신
* **쿠콘 STAR 사례** - 정산 검증, 1원 계좌 검증의 상태 보정과 거래 지연 개선, 엑셀, 파일 대사, 분할 커밋

#### 먼저 익혀 둘 답변

> 금융 백엔드와 업무용 AI 에이전트를 개발해 온 4년 차 개발자입니다. 금융 서비스에선 거래와 정산 결과를 확인하고, 요청이 몰려도 거래 처리가 지연되지 않도록 개선했습니다. 법틀에서는 대화형 계약 기안 에이전트를 기존 법무 시스템에 연결해 고객사에 공동 출시했고, 실무자가 결정을 내리기 전에 AI의 검토 의견과 원문 근거를 확인하는 기능을 개발했습니다. 앞으로도 사용자가 AI 결과를 확인하고 실제 판단에 활용할 수 있는 업무 시스템을 만들고 싶습니다.

#### STAR로 답하는 법

| 단계     | 한 문장으로 답할 질문             | 면접에서 꺼낼 내용                           |
| ------ | ------------------------ | ------------------------------------ |
| S · 상황 | 사용자가 무엇 때문에 불편했나?        | 사용자와 기존 흐름, 실패가 드러난 지점               |
| T · 과제 | 팀 목표 중 내가 맡은 범위는 어디까지였나? | 직접 구현한 부분, 협업 지점, 지켜야 한 제약           |
| A · 행동 | 원인을 어떻게 확인했고 무엇을 선택했나?   | 관찰 근거 하나, 설계 선택 하나, 처리 순서            |
| R · 결과 | 어떤 근거로 어디까지 결과를 말할 수 있나? | 공동 출시, 브랜치 반영, 기능 개발, 정량 지표 중 확인된 범위 |

처음에는 사례당 60\~90초를 목표로 상황과 역할을 짧게 말한다. 이어 “왜 그렇게 구현했나요?”라는 질문에는 다른 선택지와 그때 고려한 기준을 답한다. 실제로 비교했던 선택과 지금이라면 검토할 대안을 구분해 두면 기억이 흐릿해도 설명을 이어갈 수 있다.

#### 복습할 때 남길 메모

* 사례마다 “내가 직접 바꾼 것”을 동사 세 개로 적는다.
* 먼저 그림을 그린다. 입력 → 상태 변화 → 결과 소비 지점 → 실패 시 복구 경로만 적어도 흐름이 떠오른다.
* 수치나 설정값이 기억나면 근거를 찾아 날짜와 함께 기록한다. 수치가 가물가물한 상태에선 적용 범위와 바뀐 동작부터 설명한다.
* 출시 후 개선에 대해 질문받으면 경험과 다음에 검증하고 싶은 항목을 나눠 말한다. 에이전트라면 검토 의견의 채택·미반영 사유와 근거 불일치 유형, 금융 배치라면 예외 건과 재처리 결과가 검증의 출발점이 된다.

### 법틀 STAR 사례

법무 시스템에 대화형 계약 작성을 연결한 출시 사례와, 계약 관련 결정을 내리기 전 AI 의견을 확인하는 기능의 개발 사례가 있다. 두 경험 모두 실제 사용자가 어떤 단계에서 결과를 받아 무엇을 하는지부터 설명한다.

#### 1. 대화형 계약 기안 에이전트 개발과 고객 출시

* **S · 상황** - 사용자가 계약서 작성을 위해 정보를 여러 번 주고받는데, 단일 메시지만 모델에 보내면 앞에서 합의한 조건과 첨부 문서의 내용을 후속 질문에서 활용하기 어려웠다. 대화 결과가 계약 작성 화면에 이어져야 실제 업무에서 사용할 수 있었다.
* **T · 과제** - 대화와 첨부 내용을 보존하고, 사용자 요청에 맞게 처리 경로를 연결하며, 계약 작성을 시작할 때 기존 입력 양식을 재사용할 수 있도록 했다.
* **A · 행동**
  * LangGraph 상태 그래프에서 요청 유형에 맞춰 처리 흐름을 나눴다. 이전 메시지와 파일에서 추출해 저장한 텍스트를 같은 대화의 이후 요청에 함께 전달했다.
  * PDF·DOCX 첨부 처리와 메시지 저장 흐름을 연결했다. 앞서 입력한 계약 조건이 다음 질문에서도 맥락으로 이어지게 했다.
  * 대화에서 정리한 계약 정보를 기존 계약 입력 화면이 읽을 수 있는 값으로 변환했다. 사용자가 추천 양식을 선택하면 기존 작성 화면을 열고 필요한 값을 채울 수 있도록 연결했다.
* **R · 결과** - 사용자가 기존 법무 시스템 안에서 AI와 대화하고 계약서 초안을 작성하는 기능을 팀과 함께 기업 고객 2곳에 출시했다.

**60초 답변 예시**

> 계약 작성은 한 번의 질문으로 끝나기 어렵고, 사용자가 이미 전달한 조건과 파일을 후속 질문에도 반영해야 했습니다. 같은 대화의 메시지와 문서에서 추출한 텍스트를 저장해 문맥으로 가져오고, LangGraph에서 요청에 따라 처리 순서를 나눴습니다. 대화에서 얻은 값은 기존 계약 양식에 연결해 사용자가 익숙한 화면에서 작성 작업을 이어갈 수 있게 했습니다. 이 기능을 팀과 함께 기업 고객 두 곳에 출시했습니다.

**복습할 질문** - 그래프 상태와 DB의 대화 이력은 각각 무엇을 책임졌나? 첨부 파일을 후속 턴에 어떻게 다시 읽었나? 기존 양식의 필드와 에이전트 출력이 맞지 않을 때 어떻게 처리했나? 직접 담당한 범위는 메시지/API, 화면 연동, 출시 중 어디였나?

**돌아볼 기록** - LangGraph 기본 흐름 · 첨부 문맥 · 계약 작성 화면 연동

#### 2. 계약 의사결정 전 AI 검토와 업무 흐름 연동

* **S · 상황** - 계약안을 수정하거나 정식 검토에 넘길 때 실무자가 그 전에 AI에게 검토 의견 초안을 요청하고 싶었다. 판단에 쓰려면 의견이 어느 원문을 근거로 나왔는지 확인할 수 있어야 하고, 계약이 변경되면 이전 결과를 현재 결과로 오인하는 문제도 막아야 했다.
* **T · 과제** - 기존 계약 업무에 검토 실행과 결과 확인을 넣고, 실무자의 판단 과정이 이후 정식 검토로 이어지도록 개발했다.
* **A · 행동**
  * 검토를 비동기 작업으로 접수하고 요청별 상태와 결과를 조회할 수 있게 했다. 실행 당시 계약과 적용 기준을 기준으로 결과를 연결했다.
  * 모델이 인용한 구절을 계약서 원문과 구절별로 대조했다. 떨어진 여러 구절은 각각 원문에서 위치를 찾고, 일치하지 않는 근거가 있는 항목은 제외하는 규칙을 적용했다. 조항 연결과 원문 강조를 검토 화면에 반영했다.
  * 저장 시 계약 정보나 본문·파일의 실제 변경 여부를 구분했다. 값이 같으면 결과를 유지하고, 바뀌면 현재 결과를 무효화해 다시 검토하게 했다. 완료된 과거 결과는 검토 당시 내용과 함께 이력에 남겼다.
  * 반영한 내용, 반영하지 않은 사유, 추가 정보를 정식 검토 요청에 연결했다. 이후 검토자는 무엇을 확인하고 어떤 판단을 했는지 이어서 볼 수 있었다.
* **R · 결과** - 기존 업무에서 검토 요청 → 의견·근거 확인 → 수정 또는 미반영 판단 → 정식 검토 요청으로 이어지는 기능을 개발했다. 11월 17일 기준 관련 작업이 기준 브랜치에 반영됐다. 운영 배포, 전체 흐름 QA, 사용성 지표는 이후 상태를 다시 확인한다.

**60초 답변 예시**

> 실무자가 계약 관련 결정을 내리기 전 AI에 검토 의견 초안을 요청하고, 판단 근거를 함께 확인하는 흐름을 개발했습니다. AI가 인용한 문장은 계약서 원문과 대조해 실제 위치를 찾고, 계약이 바뀌면 이전 결과는 이력에 두고 최신 내용으로 다시 판단하도록 했습니다. 실무자가 반영한 내용과 반영하지 않은 이유도 검토 요청에 연결해 이후 검토자가 판단의 맥락을 볼 수 있도록 했습니다.

**복습할 질문** - 글자가 달라도 의미가 같으면 왜 제외할 수 있는가? 원문 일치가 의견의 타당성을 어디까지 보장하는가? 단순 저장과 실제 변경은 어디에서 판별했는가? 계약 내용이 바뀌는 동안 이전 작업의 결과가 도착하면 어떻게 처리되는가? AI 의견을 넘기는 흐름에서 사람이 내리는 결정은 무엇인가?

**돌아볼 기록** - 프로젝트 통합 상태 · 비동기 검토 API · 구절별 근거 · 실행 상태와 중복 처리 · 변경 감지와 이력 · 검토 요청 연결

#### 3. 기능별 LLM 후보 비교와 적용 판단

* **S · 상황** - AI가 쓰이는 기능마다 놓치면 안 되는 항목, 허용할 수 있는 오탐, 사용자가 기다릴 수 있는 시간, 비용이 다르다. 모델의 이름이나 단가만 보고는 업무에 적합한지 판단하기 어려웠다.
* **T · 과제** - 같은 기능과 입력 조건에서 모델·추론 설정 후보를 비교해 적용 후보를 판단했다.
* **A · 행동**
  * 비교하려는 모델·추론 설정을 달리하고 입력·프롬프트 등 비교 조건을 맞췄다. 계약 검토 기능의 비교 기록에는 10월 27\~28일 같은 조건의 완료 조합 93쌍이 남아 있다.
  * 업무에 필요한 필수 항목 탐지와 불필요한 지적을 확인하고 응답시간과 비용을 함께 비교했다. 제한된 표본에서 후보의 속도 순위가 비교 일자에 따라 달라지는 것도 확인했다.

### 쿠콘 STAR 사례

결제·정산 배치는 후속 이체·출금에 쓸 금액을 검증했다. 1원 계좌 검증은 같은 서비스의 두 문제인 거래 상태 미확정과 요청 집중 시 거래 지연을 각각 다뤘다. 결제 중계의 파일 대사와 가맹점 정보 갱신은 별도 작업이다.

#### 1. 검증된 정산 금액으로 이체·출금할 수 있도록 배치 개발

* **S · 상황** - 결제 결과가 확정되지 않은 거래가 있었고, 결제사가 가진 기록과 내부 정산 데이터가 다를 수 있었다. 후속 이체·출금에 사용하려면 어떤 금액이 검증을 거쳤는지 판단할 수 있어야 했다.
* **T · 과제** - 미확정 거래의 결제 상태를 다시 확인하고 외부 결제 기록과 내부 정산 데이터를 대조하는 배치를 개발했다.
* **A · 행동**
  * 결과가 확정되지 않은 건은 재조회할 수 있도록 처리했다. 최초 응답이 늦거나 타임아웃이 발생했을 때, 승인 여부를 그 응답만으로 확정하기 어려웠기 때문이다.
  * 결제사가 보유한 기록과 내부 정산 데이터를 비교해 불일치를 확인했다. 거래 상태 재확인과 금액 검증을 거쳐 후속 거래에 검증된 정산 금액을 사용할 수 있도록 연결했다.
  * 면접에서 설명할 실제 비교 키, 취소·부분 환불 처리, 불일치 시 보류 방식은 당시 명세나 본인 기록에서 확인한다.
* **R · 결과** - 검증된 정산 금액으로 이체·출금할 수 있는 배치를 개발했다. 개발 후 퇴사했으므로 확인한 성과는 개발 범위까지다. 운영 이후 처리 건수와 정산 이슈 감소율은 별도 기록이 필요하다.

**60초 답변 예시**

#### 2. 1원 계좌 검증의 미확정 거래 상태 보정

* **S · 상황** - 계좌 검증을 위해 1원 이체를 요청했는데 은행 응답이 늦어 거래가 내부에서 ‘처리 중’으로 계속 남는 경우가 있었다. 외부에서는 뒤늦게 처리됐더라도 내부가 확정 상태를 알지 못할 수 있었다.
* **T · 과제** - 늦게 응답하는 거래를 다시 확인하고, 내부 기록이 외부 거래 상태와 맞도록 보정 경로를 개선했다.
* **A · 행동**
  * 미확정 상태로 남은 데이터를 살펴보고, 은행 처리 지연을 감안해 재조회 대상 조건과 처리 주기를 조정했다.
  * 조회 결과로 내부 상태를 보정했다. 초기 기록에는 재조회 대상 대기 기준을 3분에서 5분으로 조정했다는 설명과, 1분마다 ‘5분 전 데이터’를 조회했다는 설명이 있다. 1분은 실행 주기, 5분은 대상 대기 조건으로 해석할 수 있지만 실제 비교 연산과 대상 구간은 코드를 확인한다.
* **R · 결과** - 이력서 기준 데이터 정합성 오류 95% 이상 감소. 무엇이 오류 한 건이었는지, 일정 기간의 건수인지 거래 대비 비율인지, 전후 대상과 기간은 원래 집계를 확인한다.

**45초 답변 예시**

> 1원 계좌 검증을 요청했을 때 은행 응답이 늦어 내부 거래가 계속 처리 중으로 남는 문제가 있었습니다. 너무 이른 조회로는 최종 상태를 알 수 없는 경우가 있어 재조회 대상 조건과 실행 주기를 조정했습니다. 이후 확인한 외부 상태를 반영해 미확정 상태를 보정했습니다. 이력서에 기록한 95% 이상 감소는 이 상태 정합성 문제에 대한 지표입니다.

**복습할 질문** - 조회 대기 시간을 늘리면 사용자에게 어떤 비용이 생기나? 이미 종료된 상태를 다시 바꿀 수 있는가? 늦은 콜백과 배치 갱신이 겹치면 무엇을 우선할 것인가? 미확정이 오래 지속되는 거래가 수동 확인으로 넘어가는 기준이 있었나?

#### 3. 1원 계좌 검증에서 집계 병목을 거래 처리와 분리

* **S · 상황** - 계좌 검증 요청이 몰리면 각 거래의 실시간 집계 갱신이 같은 데이터에 집중됐다. 집계에서 발생한 DB 잠금 때문에 사용자가 기다리는 거래 처리까지 밀렸다.
* **T · 과제** - 계좌 검증 흐름은 계속 처리하면서, 집계에 필요한 갱신이 거래 처리의 병목이 되지 않도록 바꿨다.
* **A · 행동**
  * 요청이 늘어날 때 병목이 나타나는 구간을 확인하고, 실시간 집계의 DB 잠금과 거래 지연의 관계를 찾아냈다.
  * 거래 처리에서 즉시 갱신하던 집계를 분리해 일 단위 배치에서 처리하도록 변경했다. 거래 결과를 확정하는 데 필요한 작업과 운영 집계의 시점을 분리했다.
* **R · 결과** - 이력서 기준 요청 집중 상황의 거래 지연율 95% 이상 감소. 이는 거래 상태 보정과 다른 사례 및 지표다. 지연으로 분류하는 기준과 전체 거래 대비 집계 조건은 원래 기록을 확인한다.

**45초 답변 예시**

> 같은 1원 계좌 검증에서 요청이 몰릴 때는 실시간 집계 갱신이 DB 잠금을 일으켜 거래까지 지연됐습니다. 요청마다 하던 집계를 거래 처리 경로에서 떼어 일 단위 배치로 옮겼습니다. 실시간으로 갱신해야 할 이유가 없는 집계가 거래 완료를 막는 상황을 줄였고, 이력서에는 거래 지연율이 95% 이상 감소했다고 기록했습니다.

**복습할 질문** - 집계가 하루 늦게 나타나도 되는지 누구와 확인했는가? 거래 처리 경로에서 여전히 남겨야 할 쓰기는 무엇이었는가? DB 락을 확인한 로그나 쿼리가 있었나? 필수 실시간 집계였다면 비동기 큐·시간 버킷·쓰기 분산 중 무엇을 검토할 것인가?

#### 4. 대용량 엑셀 다운로드 메모리 병목 개선

* **S · 상황** - 운영 화면에서 대량 데이터를 엑셀로 내려받을 때 조회 결과와 파일 생성 객체가 메모리를 많이 사용해 다운로드가 실패했다.
* **T · 과제** - 데이터를 조회하고 엑셀로 출력하는 과정에서 최대 메모리 사용량을 줄여 대량 다운로드를 가능하게 했다.

#### 6. 가맹점 정보 갱신 배치의 분할 커밋

* **S · 상황** - 가맹점 정보를 대량으로 저장·갱신하는 배치에 시간이 오래 걸렸다. 한 실행에서 많은 데이터를 처리할 때 트랜잭션 경계를 어떻게 잡는지가 중요했다.
* **T · 과제** - 가맹점 데이터 갱신 작업을 개선해 대량 갱신에 걸리는 시간을 줄였다.
