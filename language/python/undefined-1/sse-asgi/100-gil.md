# 동시 스트림 100개의 청구서 — 스레드 비용, GIL 천장, 붕괴 지점 실측

> [상위 노트](../)는 "왜 ASGI + async iterator 여야 하는가"를 다뤘다. 하지만 거기서 채택한 구조(`sync_to_async` 브릿지)는 **동시 스트림 1개당 OS 스레드 1개**를 쓴다. 그럼 동시 요청이 100개면 스레드가 100개 생기는가? 그 비용은 얼마인가? 어디서 무너지는가? 이 노트는 그 세 질문에 **숫자로** 답한다.
>
> 실측 환경: Python 3.11.15 / 8 코어 / 15.7GB RAM / Linux, `asgiref` + Django 5.2 계열. 모든 표는 직접 실행한 결과이며, 절대값은 환경마다 다르지만 **비율과 곡선의 모양**은 재현된다.

***

## 0. 결론 먼저

| 통념                     | 실측                                             |
| ---------------------- | ---------------------------------------------- |
| "스레드 100개는 메모리를 많이 쓴다" | **RSS +2.9MB.** 무해하다                           |
| "스레드를 늘리면 처리량이 늘어난다"   | **8코어에서도 처리량 완전 평탄.** GIL                      |
| "스레드가 많으면 느려진다"        | **대기만 하면 500개도 무해**(p99 0.89ms). CPU를 원할 때만 재앙 |
| "진짜 병목은 스레드 수"         | 진짜 병목은 **청크당 경계 통행 CPU**와 **스레드에 딸려오는 DB 커넥션** |

한 줄 요약: **스레드 100개의 청구서는 3MB짜리 영수증이다. 진짜 청구서는 GIL과 커넥션 풀에서 온다.**

## 1. 정말 요청당 스레드 1개인가 — 소스와 실측

### 소스 근거: 컨텍스트마다 `max_workers=1` 풀을 새로 만든다

`asgiref/sync.py`의 `SyncToAsync.__call__`:

```python
elif self.thread_sensitive_context.get(None):
    thread_sensitive_context = self.thread_sensitive_context.get()
    if thread_sensitive_context in self.context_to_thread_executor:
        executor = self.context_to_thread_executor[thread_sensitive_context]   # 재사용
    else:
        executor = ThreadPoolExecutor(max_workers=1)                           # ★ 새로 생성
        self.context_to_thread_executor[thread_sensitive_context] = executor
```

그리고 Django의 ASGI 핸들러는 **요청마다** 그 컨텍스트를 연다:

```python
# django/core/handlers/asgi.py
async with ThreadSensitiveContext():
    await self.run_get_response(request)
```

두 사실을 곱하면 결론이 나온다: **요청 1개 = 컨텍스트 1개 = `max_workers=1` 풀 1개 = 스레드 1개.** 그리고 결정적으로, `context_to_thread_executor`는 `WeakKeyDictionary`일 뿐 **개수 상한이 없다.** 즉 이 구조에는 스레드 풀의 캡이 존재하지 않는다.

### 실측: 동시 요청 100개

```
시작 시점:                  active_count=1     VmRSS=21.2 MB
스트림 100개 전부 활성인 순간:  active_count=101   VmRSS=24.1 MB  (+2.9 MB)
청크를 꺼낸 서로 다른 스레드:   100개  →  요청 1개당 1.00개
요청 전부 종료 + GC 후:       active_count=1     VmRSS=23.8 MB
```

1:1이 정확히 확인된다. 회수도 확인된다 — `ThreadPoolExecutor`는 자기 자신에 대한 weakref 콜백을 워커 스레드에 넘겨두므로, 컨텍스트가 죽고 executor가 GC되면 큐에 `None`이 들어가 스레드가 스스로 종료한다. **스레드 수명 ≈ 요청 수명**이고 누수는 없다.

### 함정: 컨텍스트가 없으면 전역 1개 스레드로 직렬화된다

같은 `__call__`의 마지막 분기:

```python
else:
    executor = self.single_thread_executor   # 클래스 속성 = 프로세스 전역 공유, max_workers=1
```

Django 요청 밖에서(관리 명령, 커스텀 asyncio 엔트리포인트, 직접 만든 `asyncio.run`) `sync_to_async(..., thread_sensitive=True)`를 부르면 **프로세스 전체가 스레드 1개를 줄 서서 쓴다.** 동시성이 조용히 1이 되는 함정이라, 벤치마크가 이유 없이 직렬로 보이면 여기를 먼저 의심한다.

## 2. 스레드 1개의 청구서 — 통념 교정

### 메모리: 예약은 MB, 실사용은 KB

| 파킹된 스레드 수 | VmRSS   | VmSize(가상) | RSS/스레드     | VSZ/스레드 |
| --------- | ------- | ---------- | ----------- | ------- |
| 0         | 16.0 MB | 29 MB      | —           | —       |
| 100       | 17.6 MB | 4.8 GB     | 16.6 KB     | \~49 MB |
| 500       | 25.9 MB | 8.1 GB     | 20.2 KB     | \~16 MB |
| 1,000     | 35.6 MB | 12.1 GB    | **20.1 KB** | \~12 MB |

`ulimit -s`가 8192KB라 스레드마다 스택 8MB를 **가상 주소로 예약**하지만, 실제로 건드린 페이지만 물리 메모리가 된다 — 파킹된 스레드는 **20KB**다. "스레드는 8MB"라는 통념은 VSZ를 RSS로 착각한 것이다.

{% hint style="warning" %}
VSZ가 무해한 것은 리눅스 overcommit이 켜져 있고 컨테이너 메모리 제한이 RSS 기준(cgroup)일 때다. `ulimit -v`를 걸거나 overcommit을 끈 환경에서는 스레드 1,000개의 12GB 예약이 그대로 실패 요인이 된다.
{% endhint %}

### 생성·소멸 시간

```
  100개 생성+start:  12.7 ms  (127 µs/스레드)   |  종료 회수:   2.9 ms
1,000개 생성+start:  86.2 ms  ( 86 µs/스레드)   |  종료 회수:  85.2 ms
```

수십 초짜리 스트림 하나를 여는 비용에서 86µs는 반올림 오차다. **생성 비용도 병목이 아니다.**

### 동시성 단위 1개의 원가 비교

```
asyncio task 1개 :  1.14 KB RSS   (10,000개 기준)
OS 스레드 1개    : 17.54 KB RSS   ( 1,000개 기준)
→ 15배
```

15배지만 **절대값이 작아서** 메모리만 보면 둘 다 싸다. 스레드가 비싼 이유는 메모리가 아니라 다음 두 절에 있다.

## 3. 진짜 비용 ① GIL — 처리량은 스레드로 늘지 않는다

실제 SSE 청크 1개를 가공하는 작업(`json.dumps` + `data: ...\n\n` 조립)을 N개 스레드가 동시에 반복했다. **코어는 8개다.**

| 스레드 수 | 총 청크/초  | 1스레드 대비   | 스레드당 청크/초 |
| ----- | ------- | --------- | --------- |
| 1     | 629,873 | 1.00x     | 629,873   |
| 2     | 621,048 | 0.99x     | 310,524   |
| 4     | 619,375 | 0.98x     | 154,844   |
| 8     | 615,930 | 0.98x     | 76,991    |
| 16    | 607,786 | **0.96x** | 37,987    |

총량이 완전히 평탄하다. 8코어를 줘도 **파이썬 프로세스 1개가 쓸 수 있는 CPU는 실질적으로 코어 1개**다. 스레드를 늘리면 같은 파이를 더 얇게 나누기만 하고(스레드당 처리량이 정확히 1/N), 16개에서는 전환 비용으로 **오히려 4% 손실**이 난다.

> 이 표가 곧 다음 규칙이다: **스레드는 대기를 겹치는 도구이지, 계산을 늘리는 도구가 아니다.** 계산을 늘리려면 프로세스(워커)를 늘려야 한다.

***

## 4. 진짜 비용 ② 대기하는 스레드는 공짜, CPU를 원하는 스레드는 재앙

스트림 1개가 20ms 주기로 청크를 전달해야 한다고 하고, **목표 시각 대비 얼마나 밀리는지**를 배경 부하별로 측정했다.

| 배경 부하               | p50           | p99             | max         |
| ------------------- | ------------- | --------------- | ----------- |
| 없음 (스트림 1개뿐)        | 0.30 ms       | 0.99 ms         | 3.22 ms     |
| **대기 위주** 스레드 100개  | 0.21 ms       | 1.06 ms         | 1.89 ms     |
| **대기 위주** 스레드 500개  | 0.12 ms       | 0.89 ms         | 1.72 ms     |
| **CPU 활성** 스레드 8개   | 22.36 ms      | 135.77 ms       | 155.74 ms   |
| **CPU 활성** 스레드 100개 | **512.33 ms** | **2,454.37 ms** | 2,474.33 ms |

이 표가 이 노트의 심장이다.

* **대기 위주 스레드 500개는 지연을 전혀 만들지 않는다.** 오히려 측정치가 미세하게 좋다(스케줄러가 자주 깨어나 타이머 정밀도가 올라간 효과). 스트림의 삶은 99%가 `recv` 대기이므로, 현실의 스트림 100개는 **이 줄에 해당한다.**
* **CPU 활성 스레드가 8개만 되어도** 20ms 주기가 p50 22ms로 밀린다 — 목표의 절반 속도다. 코어가 8개인데도 그렇다(§3).
* **CPU 활성 100개면 p99가 2.45초.** 사용자에게는 "타이핑이 뚝뚝 끊긴다"로 보인다.

결론: **스레드 개수 자체를 걱정할 필요는 없다. 걱정할 것은 "그 스레드들이 동시에 CPU를 원하는 순간"이다.** 그리고 다음 절이 밝히듯, `sync_to_async` 브릿지는 청크마다 그 순간을 만든다.

***

## 5. 진짜 비용 ③ 경계 통행 자체가 청크당 CPU를 태운다

### 청크 1개를 경계 넘기는 순수 오버헤드

upstream 대기를 0으로 두고 청크 20,000개를 흘려 순수 오버헤드만 측정했다.

| 경로                                                      | µs/청크      |
| ------------------------------------------------------- | ---------- |
| 동기 루프에서 `next()` 직접                                     | 1.54       |
| 순수 async 제너레이터 `async for`                              | **1.45**   |
| `await sync_to_async(next, thread_sensitive=True)(gen)` | **128.15** |
| └ 그중 `contextvars.copy_context()` (호출마다 1회)             | 0.02       |

**브릿지 왕복은 순수 async 대비 88배 비싸다.** 그리고 이 비용은 청크 크기와 **무관**하다 — 왕복(루프 → executor 스레드 깨움 → 실행 → future 완료 → 루프 복귀) 자체의 값이다. `copy_context`처럼 의심하기 쉬운 항목은 무죄고(0.02µs), 비용은 전부 **스레드 핸드오프**에 있다.

### 그 128µs는 병렬화되는가? — 아니다, 루프의 직렬 구간이다

이벤트 루프는 **스레드 1개**다(상위 노트 §4). 모든 청크는 루프를 정확히 한 번 통과해야 한다. 따라서 왕복 비용은 스트림별로 나뉘지 않고 **하나의 직렬 구간에 누적**된다. 확인해보면:

| 방식       | 동시  | 완료       | 청크/초       | CPU초 | **CPU점유** | µs CPU/청크 | 루프 p99 지연    |
| -------- | --- | -------- | ---------- | ---- | --------- | --------- | ------------ |
| 브릿지      | 10  | 462 ms   | 865        | 0.19 | 42%       | 487.5     | 2.78 ms      |
| 브릿지      | 50  | 804 ms   | 2,488      | 0.93 | 116%      | 465.3     | 23.03 ms     |
| 브릿지      | 100 | 988 ms   | 4,047      | 1.05 | 107%      | 263.7     | 31.13 ms     |
| 브릿지      | 200 | 1,622 ms | 4,934      | 1.99 | 123%      | 248.4     | 60.50 ms     |
| 브릿지      | 400 | 3,232 ms | **4,950**  | 4.70 | **145%**  | 293.5     | **89.77 ms** |
| 순수 async | 10  | 423 ms   | 945        | 0.01 | 3%        | 35.1      | 2.17 ms      |
| 순수 async | 50  | 438 ms   | 4,571      | 0.03 | 6%        | 14.1      | 2.28 ms      |
| 순수 async | 100 | 449 ms   | 8,905      | 0.04 | 9%        | 9.8       | 2.33 ms      |
| 순수 async | 200 | 441 ms   | 18,137     | 0.08 | 18%       | 10.2      | 1.62 ms      |
| 순수 async | 400 | 440 ms   | **36,376** | 0.11 | **25%**   | **6.7**   | 2.87 ms      |

* 브릿지는 **청크당 CPU 250\~490µs**를 태운다. 순수 async는 **7\~35µs**. 25\~50배 차이.
* 브릿지의 CPU 점유가 100%를 넘는다(최대 145%) — 커널 컨텍스트 스위칭과 GIL 핸드오프가 여러 스레드에 흩어져 코어 1개분 이상을 소모하는데, 정작 **처리량은 4,950에서 멈춘다.** 태운 CPU가 일이 아니라 조율에 쓰인 것이다.
* 브릿지의 **루프 p99 지연이 2.78ms → 89.77ms**로 증가한다. 루프가 밀리면 그 워커의 **모든 스트림**이 같이 밀린다.
* 순수 async는 400 스트림에서도 CPU 25%, 루프 지연 2.87ms로 **여유가 남아 있다.**

## 6. 붕괴 지점 — 무릎은 어디인가

스트림당 청크 40개, upstream 간격 10ms. **이상적 완료 시간은 400ms**이고, 그 초과분이 곧 경합 비용이다.

| 방식       | 동시 스트림 | 스레드 증가 | 완료       | 이상 대비     | 총 청크/초     |
| -------- | ------ | ------ | -------- | --------- | ---------- |
| 브릿지      | 1      | 1      | 435 ms   | 1.09x     | 92         |
| 브릿지      | 10     | 10     | 446 ms   | 1.12x     | 896        |
| 브릿지      | 50     | 50     | 558 ms   | 1.39x     | 3,584      |
| 브릿지      | 100    | 100    | 607 ms   | **1.52x** | 6,592      |
| 브릿지      | 200    | 200    | 1,089 ms | **2.72x** | 7,348      |
| 브릿지      | 400    | 400    | 2,313 ms | **5.78x** | 6,917 ← 감소 |
| 순수 async | 1      | 0      | 434 ms   | 1.09x     | 92         |
| 순수 async | 10     | 0      | 436 ms   | 1.09x     | 918        |
| 순수 async | 50     | 0      | 451 ms   | 1.13x     | 4,437      |
| 순수 async | 100    | 0      | 443 ms   | 1.11x     | 9,029      |
| 순수 async | 200    | 0      | 440 ms   | 1.10x     | 18,187     |
| 순수 async | 400    | 0      | 457 ms   | **1.14x** | 35,029     |

곡선의 모양을 읽으면:

* **브릿지의 무릎(knee)은 50\~100 사이.** 100에서 이미 1.5배 느려지고, 200에서 2.7배, 400에서 5.8배로 지수적으로 무너진다.
* **처리량은 200에서 포화하고 400에서 오히려 줄어든다**(7,348 → 6,917). 즉 무릎을 넘긴 뒤 요청을 더 받는 것은 **처리량을 사지 못하고 지연만 산다.** 전형적인 thrashing.
* **순수 async는 400까지 1.14x로 평탄**하고 처리량이 선형으로(92 → 35,029) 늘어난다. 아직 천장이 아니다.
* 브릿지 천장은 두 번의 독립 측정에서 **4,950 \~ 7,348 청크/초** 범위로 나왔다(계측기 부하 유무 차이). 청크당 왕복 128\~250µs의 역수와 일치한다 — **천장의 정체가 왕복 비용의 직렬 누적임이 확증된다.**

### 실무 환산

LLM 스트리밍이 스트림당 **초당 25청크** 정도를 뿜는다고 하면:

```
브릿지 :  5,000 청크/초 ÷ 25 =  200 스트림/프로세스  ← 단, 100에서 이미 지연 1.5배
순수async: 35,000 청크/초 ÷ 25 = 1,400 스트림/프로세스  ← 아직 천장 아님
```

운영 상한은 무릎이 아니라 \*\*무릎의 60\~70%\*\*로 잡는다(버스트·GC·다른 요청과 공유하므로). 브릿지 구조라면 **프로세스당 동시 스트림 60\~120개**가 현실적인 안전선이다.

## 7. 스레드에 딸려오는 자원 — 실무에서 제일 먼저 터지는 것

지금까지는 CPU 이야기였다. 그런데 현장에서 먼저 무너지는 것은 보통 CPU가 아니다.

### DB 커넥션은 스레드마다 따로 열린다

Django의 커넥션 저장소는 **진짜 thread-local**이다:

```python
# django/db/utils.py — ConnectionHandler
thread_critical = True   # "Connections needs to still be an actual thread local,
                         #  as it's truly thread-critical."
```

`thread_sensitive=True`가 요청당 전용 스레드를 고정하는 이유가 바로 이것이다(그래야 한 요청의 ORM 호출이 같은 커넥션·같은 트랜잭션을 본다). 그 대가로 **동시 스트림 수 = 최대 DB 커넥션 수**가 된다. 계산해보면:

```
워커 프로세스 4개 × 프로세스당 동시 스트림 100개 = 커넥션 400개 요구
PostgreSQL 기본 max_connections = 100
→ 프로세스당 25 스트림에서 이미 소진
```

**CPU 천장(프로세스당 \~200)보다 커넥션 천장(프로세스당 \~25)이 8배 먼저 온다.** 그리고 이 고갈은 조용하지 않다 — 커넥션 풀러를 앞에 두면 신규 요청이 풀 대기 큐에서 대기하다 **대기 타임아웃으로 끊어진다.** 증상은 "스트림이 중간에 죽는다"로 나타나고, 원인은 CPU/메모리 지표 어디에도 안 보인다.

{% hint style="info" %}
긴 스트림은 이 문제를 증폭한다. 일반 API는 커넥션을 수십 ms 쥐지만, 스트림은 **30\~120초** 동안 스레드를(그리고 그 스레드가 한 번이라도 ORM을 쓰면 커넥션을) 점유한다. 동시 점유량 = 도착률 × 점유시간(리틀의 법칙)이므로, 점유시간이 1,000배면 같은 트래픽에서도 필요 커넥션이 1,000배다.
{% endhint %}

### 청구서 총정리 — 동시 스트림 100개

| 항목            | 100개 총량     | 판정                             |
| ------------- | ----------- | ------------------------------ |
| RSS           | +2.9 MB     | 무해                             |
| VSZ(가상 예약)    | \~1.2 GB    | 조건부(overcommit·`ulimit -v` 확인) |
| 스레드 생성 시간     | 12.7 ms     | 무해                             |
| 대기 중 CPU      | \~0         | 무해                             |
| **청크 전달 CPU** | 250µs × 청크율 | **주범**                         |
| **DB 커넥션**    | 최대 100      | **주범 (보통 1순위)**                |
| 루프 p99 지연     | 2.8 → 31 ms | 위 둘의 결과                        |

## 8. 천장 계산법 — 네 개의 천장 중 min()

프로세스 1개 기준으로 각 천장을 따로 구하고 **가장 낮은 것**을 취한다.

```
① 메모리 천장  = 가용 RSS ÷ 20KB
                 → 실질적으로 무한 (1GB면 5만 개)

② CPU/GIL 천장 = (1,000,000 µs/초 × 1코어) ÷ (청크당 CPU µs) ÷ (스트림당 청크/초)
                 브릿지  : 1,000,000 ÷ 250 ÷ 25 =  160 스트림
                 순수async: 1,000,000 ÷  10 ÷ 25 = 4,000 스트림

③ 커넥션 천장  = (DB max_connections ÷ 워커 수) - 여유분
                 100 ÷ 4 = 25 스트림          ← 보통 여기가 최솟값

④ 업스트림 천장 = LLM API 동시 요청 한도 ÷ 워커 수
```

실제 한계 = **min(①②③④)**. 이 계산에서 얻는 실용적 교훈은 순서다: **③ → ② → ①** 순으로 터진다. 그래서 튜닝도 그 순서로 한다.

### 개선 레버 (ROI 순)

1. **하드 캡을 건다 (코드 0줄, 즉시)** `uvicorn --limit-concurrency N`. 초과분은 **503으로 거절**된다(`len(self.connections) >= limit` 검사). 무릎을 넘겨 전부 느려지는 것보다, 일부를 거절하고 나머지를 정상 속도로 지키는 게 낫다. asgiref에는 스레드 캡이 없으므로 **이것이 유일한 백프레셔 장치다.**
2. **커넥션 점유를 줄인다** 스트림 루프 안에서 ORM을 부르지 않는다(시작 전에 필요한 데이터를 모두 읽고, 저장은 종료 후 한 번). 스트림 도중 커넥션을 쥐지 않으면 ③ 천장이 사라진다. **가장 효과가 큰 구조 개선.**
3. **청크를 병합한다 (per-chunk 비용이 고정이므로)** 왕복 비용 250µs는 청크 크기와 무관하다(§5). 토큰 3개를 SSE 이벤트 1개로 묶으면 **루프 CPU가 1/3**이 된다. 대가는 수십 ms의 추가 지연 — 타이핑 효과에서는 지각되지 않는다. **코드 몇 줄로 천장 3배.**
4. **워커 프로세스를 늘린다** ② 천장은 프로세스당이므로 선형 확장된다. 단 ③도 같이 늘어나므로 커넥션 풀러가 전제다.
5. **순수 async로 전환한다 (async HTTP 클라이언트·async SDK)** 청크당 CPU 25배 개선 + 스레드 0 + 커넥션 문제 완화. 효과는 가장 크지만 클라이언트 계층 전면 교체라 비용도 가장 크다.

{% hint style="danger" %}
**자원이 고갈되기 전에 품질이 고갈된다.** 스레드 상한(`threads-max` 12.5만, `ulimit -u` 6.2만)에 닿기 한참 전에, 무릎(50\~100)을 넘긴 순간부터 모든 스트림이 함께 느려진다. 이때 프로세스는 죽지 않고 헬스체크도 통과하며 CPU·메모리 지표도 평온해 보인다. 그래서 **모니터링은 자원량이 아니라 "청크 간 도착 간격(p99)"을 봐야 한다** — 이 구조에서 가장 먼저 나빠지는 지표다.
{% endhint %}

## 9. 암기 카드

1. **요청 1개 = `ThreadSensitiveContext` 1개 = `max_workers=1` 풀 1개 = 스레드 1개.** 상한은 없다.
2. 파킹된 스레드는 **RSS 20KB**. "스레드 8MB"는 VSZ를 RSS로 착각한 것.
3. **처리량은 스레드로 늘지 않는다** — 8코어에서 1→16 스레드 총량 0.96x. 계산을 늘리려면 프로세스.
4. **대기하는 스레드 500개는 공짜, CPU를 원하는 스레드 8개는 재앙.** 개수가 아니라 CPU 요구가 문제다.
5. 브릿지 왕복 = **청크당 128µs 지연 / 250µs CPU**, 순수 async는 1.45µs / 10µs. **88배 / 25배.**
6. 왕복 비용은 **청크 크기와 무관** → 청크를 N개 묶으면 비용이 1/N. 가장 값싼 레버.
7. 루프는 스레드 1개 = **모든 청크가 지나는 직렬 구간.** 그래서 천장 ≈ 1 ÷ 왕복비용(실측 5,000\~7,300 청크/초).
8. 무릎은 **50\~100**, 운영 상한은 그 **60\~70%**. 무릎을 넘으면 처리량은 안 늘고 지연만 는다.
9. 실제 한계 = **min(메모리, CPU/GIL, DB 커넥션, 업스트림)** — 터지는 순서는 보통 **커넥션 → CPU → 메모리.**
10. **자원이 아니라 품질이 먼저 고갈된다.** 볼 지표는 CPU가 아니라 **청크 도착 간격 p99.**
